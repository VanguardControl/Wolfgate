# F4 implementation plan (architect output, revision 2, 2026-09-13)

Produced by the F4 design workflow after two adversarial review passes (12 findings, all folded in; three sub-claims rejected with evidence). Orchestrator notes: C# gates run in DebugOpt; stage 8 (live-client manual pass) is deferred to a screenshot-harness session or the user's playtest and replaced in the workflow by a headless draw-smoke test; stage 9 (radar berth ghost, one marked upstream line) is included.

=== 0. HEADLINE DECISIONS AND THE EVIDENCE ===

D-A. ZERO upstream edits for the core feature; ONE marked line only for the optional radar ghost (stage 9).
 - PowerChargeComponent reads are LEGAL under [Access]. AccessAttribute.OtherDefaultPermissions = Read (RobustToolbox/Robust.Shared/Analyzers/AccessAttribute.cs:64) and Content.Server/Gravity/GravityGeneratorSystem.cs:91-93 already reads `charge.Charge` cross-type. No _WF partial of PowerChargeSystem is needed.
 - The ONLY [Access]-gated WRITE F4 needs is GravityGeneratorComponent.GravityActive (Content.Server/Gravity/GravityGeneratorComponent.cs:17-18) for the Falling push. GravityGeneratorSystem is `sealed partial` (:10), so one new _WF partial in namespace Content.Server.Gravity satisfies the friend gate. Precedent: Content.Server/_WF/PlanetCracker/Cracker/CEZLevelsSystem.WFVirtualMass.cs.
 - ForceAnchor at runtime needs no ADD helper: EntityManager.Components.cs:428-429 re-raises MapInitEvent on an already-map-initialised entity, so `AddComp<ForceAnchorComponent>` runs ForceAnchorSystem.OnForceAnchorMapInit (ForceAnchorSystem.cs:40-44) = `_shuttle.Disable(force:true)` + `EnsureComp<PreventGridAnchorChangesComponent>`. There is NO release path in ForceAnchorSystem (the file is 51 lines and subscribes only MapInit, FTLCompleted and ConsoleFTLAttempt); F4 writes it — see D-M for the asymmetry trap.
 - CEZLevelsSystem.TryEnterTransit public (CEZLevelsSystem.Transit.cs:407); TryGetGravgenLoad public (Gravity.cs:570); CEZGridConnectorSystem.MarkDirty public (:58); ShuttleSystem.GetAllDockedShuttles public (:459); DockingSystem.RedockDocks public (:74).

D-B. Part multiplier = the ARITHMETIC MEAN of the two projectors' CrackTimeMultiplier.
 REVISED JUSTIFICATION (reviewer was right that the old one overclaimed): design §5 (PLANET_CRACKER_DESIGN.md:219) states both endpoints for UNIFORM part tiers, so the mean AND the minimum both reproduce 5.6 min (d=16, both tier 4) and 20 min (d=40, both tier 1) exactly. Only the PRODUCT is excluded by the numbers — 12 x 16/24 x 0.49 = 3.92 min undershoots the stated 5.6 min floor. The mean is chosen on gameplay grounds: under the minimum rule a single-projector upgrade is worth literally nothing, so a crew that scrounges one tier-4 capacitor gets no reward. Documented in the formula's summary comment; the mixed-tier case is the only place the two rules differ and CrackTimerTest.PartMultiplierIsTheMeanOfBothProjectors pins it.

D-C. The crack timer uses TWO fields, not one deadline.
 `CrackEnd` (TimeOffsetSerializer + AutoPausedField) is authoritative while running; `CrackRemaining` banks the remainder while the damage pause holds. Map pause and damage pause are different mechanisms and must coexist. WFPlanetCrackerComponent gains the CLASS-LEVEL `AutoGenerateComponentPause` attribute — it has none today and `[AutoPausedField]` is inert without it, with no analyzer diagnostic.

D-D. Centrifuge spin and the D25 hysteresis are computed server-side, never read from PowerChargeState.
 PowerChargeSystem.UpdateUI early-returns on `!IsUiOpen` (:187) and quantises Charge to a byte (:215). WFCentrifugeSystem reads the raw float PowerChargeComponent.Charge (Content.Server/Power/Components/PowerChargeComponent.cs:59-61, range 0..1) at 4 Hz and writes Spin/AtFull/Load/Capacity. Threshold is a FRACTION of MaxCharge (:47-48, default 1), never an absolute.

D-D2 (NEW, from review). Those four values travel on BOTH channels, deliberately, because the two consumers have different visibility.
 The crack console may sit far from the centrifuge on a capital hull, so the console path takes them in WFCrackConsoleState (server-authored, PVS-proof). The centrifuge's own machine UI is opened by a player standing at the machine, which guarantees the entity is in PVS, so WFCentrifugeWindow reads the AutoNetworkedFields — NOT the byte-quantised PowerChargeState.Charge/255f the previous revision specified, which would have made the dial a different animal in each host. Section 7's old rule ("carries ONLY what is not already component-networked") is WITHDRAWN and replaced by D-N. Wire cost is controlled by quantisation, not by choosing one channel: the Spin epsilon is 0.005, not 0.001 — at the shipped chargeRate 0.00417/s (machines.yml:46) a 0.25 s sweep moves Charge by 0.00104, so a 0.001 epsilon would have dirtied the component on every single sweep for the whole 240 s spin-up. 0.005 dirties about once a second and is far finer than the 0.98/0.95 hysteresis band.

D-E. The centrifuge prototype gains `charge: 0`. PowerChargeComponent.Charge DEFAULTS TO 1 (:61) and WFCentrifuge does not override it (machines.yml:42-48), so a hull from `wfcracker spawn cracker` starts at FULL spin, contradicting the machines.yml:46 comment and making every manual spin-up check meaningless.

D-F. Cracker/centrifuge/projector links are NOT stored on the component; they are resolved by grid-child query each sweep (1 Hz, a handful of entities). AnchorA/AnchorB (WFPlanetCrackerComponent.cs:19,:23 — declared, never written) become the TARGETED pair and get their first writer in F4.

D-G (REVISED — this was a blocker). Geometry moves into a shared abstract system AND that system gets a concrete subclass ON BOTH SIDES.
 `SharedWFCrackerSystem` (abstract, Content.Shared) takes TryGetBerthCentre verbatim from WFCrackerSystem.cs:78-98 and adds TryGetBerthRect / TryGetCircle / TryGetBerthOffset / static GetCrackDuration. The server's `WFCrackerSystem : SharedWFCrackerSystem` is not enough on its own: ReflectionManager.GetAllChildren skips abstract types outright (RobustToolbox/Robust.Shared/Reflection/ReflectionManager.cs:66 `if (!baseType.IsAssignableFrom(type) || type.IsAbstract) continue;`), that enumeration is the only discovery source for EntitySystemManager.Initialize (EntitySystemManager.cs:152-166), and a base type is resolvable only through the concrete-subtype map built at :176-199. GetEntitySystem<T> is a bare Resolve (:79-83), so `_ents.System<SharedWFCrackerSystem>()` on the client would throw UnregisteredTypeException at the first Draw. The existing precedent does not cover this: the only client use of SharedWFGravityAnchorSystem is the STATIC GetCutRadius (WFCrackCircleOverlay.cs:107 against SharedWFGravityAnchorSystem.cs:4-8). F4 therefore ships Content.Client/_WF/PlanetCracker/Cracker/WFCrackerSystem.cs — `public sealed partial class WFCrackerSystem : SharedWFCrackerSystem` with no subscriptions — in stage 1, and a headless test resolves the base type on both sides so the throw can never reach a Draw.

D-H. Cross-map comparison must use raw Vector2, never MapCoordinates.InRange. The berth centre carries the ORBIT map id, the circle centre the GROUND map id; MapCoordinates.InRange returns false for differing MapIds before any distance maths (RobustToolbox/Robust.Shared/Map/MapCoordinates.cs:89-94). CE z-layers share world XY, so plain subtraction of `.Position` is the only correct route.

D-I (CORRECTED — the previous revision had this backwards for unfilled circles). Colour space, re-derived from engine source:
 * DrawPrimitives (Vector2 span): RAW skin colour — PadVerticesV2 applies Color.FromSrgb internally (DrawingHandleBase.cs:117-124).
 * DrawCircle(filled: true): RAW skin colour — Clyde.RenderHandle.cs:437-441 does `colorReal = Color.FromSrgb(color)` only in the filled branch, with the engine's own comment "Unfilled (using _renderHandle.DrawLine) does the linear conversion internally. Filled meanwhile uses DrawPrimitives, so has to do it here."
 * DrawCircle(filled: false), DrawLine, DrawRect, DrawTextureRect: `Color.FromSrgb(skinColour)` — the unfilled branch (:453-454) passes `color * Modulate` unconverted into DrawLine, which writes it straight into Vertex2D.Modulate, documented linear (Clyde.Layout.cs:43).
 * DrawString: RAW skin colour, so the diagram's text matches the stock Labels beside it.
 The shipped WFCrackCircleOverlay.cs:106-122 already states exactly this rule and does exactly this — raw into DrawPrimitives at :116, `linear` into DrawLine and into the two UNFILLED DrawCircle marks at :118-120. The previous revision cited that file while inverting half of it. The corrected rule goes in the WFDiagramControl.cs file header verbatim.
 Corollary: DrawCircle takes no segment count (divisions = Math.Max(16, radius*16), Clyde.RenderHandle.cs:431-432), so any ring that wants a fixed vertex budget — the centrifuge face ring included — uses the cached DrawPrimitives line-strip recipe, not DrawCircle.

D-J. The berth snap is refused, not attempted, when the cracker is in a CE grid network of >= 2 grids. CEZGridSyncSystem.OnGridMoved (Content.Server/_CE/ZLevels/Core/CEZGridSyncSystem.cs:119-155) intercepts any transform move of a CEZGridComponent grid; its only escape is `network.Comp.Grids.Count < 2` (:128), and with a static anchor it pins the grid straight back via ApplyAnchorToGrid (:133-141) while the state machine advances anyway. IsStaticAnchor (:170-177) returns true for any non-Dynamic body, so a ForceAnchor'd cracker MAKES its own network static-anchored: snap BEFORE force-anchoring, never after.

D-K. Falling pushes with DIFFERENT startProgress for cracker and chunk. CheckTransitCollisions' order-swap guard is `prevDelta * curDelta > 0f -> continue` (CEZLevelsSystem.Gravity.cs:193-194); two grids at identical progress give 0*0 = 0, which is not > 0, so the pair is AABB-tested every tick with `explodeGrids: true` on contact (:196-212). Cracker takes 1.0f, F5's chunk 0.98f via the WFCrackerFallingEvent hook.

D-L. Cloud-layer decision: DROP IT for crackable planets, raising airLayers 2 -> 3. See `cloud_layer_decision`.

D-M (NEW, from review). EngageLock must guarantee the hull is releasable before it locks it.
 ShuttleSystem.Enable and Disable are NOT symmetric: Enable resolves ShuttleComponent as a required dependency (`Resolve(uid, ref manager, ref component, ref shuttle, false)`, Content.Server/Shuttles/Systems/ShuttleSystem.cs:201-204) and silently returns when it is missing, while Disable resolves only FixturesComponent and PhysicsComponent (:214-218). ForceAnchorSystem only ever calls the Disable side (:42,:48). So a cracker hull without ShuttleComponent can be force-anchored and never released — BodyType stays Static, with no log, which breaks the abort path AND the Falling push (whose step 1 depends on Enable having actually flipped the body to Dynamic before TryEnterTransit). The test hull is saved only by WFTestGridFactory.cs:141 `EnsureComp<ShuttleComponent>(grid.Owner)`, i.e. the bug would have been invisible in tests. EngageLock therefore refuses and Log.Errors when the hull lacks ShuttleComponent, and ReleaseLock asserts its own post-condition by reading PhysicsComponent.BodyType after Enable and Log.Erroring if it is still Static.

D-N (NEW, from review). Derived geometry travels in the BUI state and on the GRID component; it is NOT re-derived client-side off the berth marker or the projectors.
 Grid membership is not a PVS exemption. net.pvs_range defaults to 25 tiles (RobustToolbox/Robust.Shared/CVars.cs:232) and this repo overrides it nowhere. The berth marker sits 26 tiles past its own marker on a 48x48 berth (WFChunkBerthComponent.cs:13,:17), on a MarkerBase prototype (consoles.yml:43) no player ever has reason to stand near, and berth-side projectors on a capital hull are routinely past 25 tiles from the bridge. Anchors are the only PlanetCracker entities with a global override — `grep -rn CEPvsOverride Content.Server/_WF Content.Shared/_WF` returns exactly WFGravityAnchorSystem.cs:115 and :148, nothing for the berth or the projectors. Had the diagram re-derived these client-side it would have silently drawn no berth rectangle, no tolerance ring, no offset arrow and an empty projector panel while the server state said nominal.
 Fix, in two parts, and deliberately NOT the reviewer's alternative of adding CEPvsOverrideComponent to the berth marker and every projector (that pays permanent PVS cost on every client for data only one open window wants):
  (a) WFCrackConsoleState carries the derived geometry directly — berth centre (Vector2 world XY), berth half-extents, berth world rotation, the hull LocalAABB, the circle centre and radius, and a small per-projector record list (grid-local position, WFProjectorState, powered, broken). A few dozen bytes at 0.25 s.
  (b) WFPlanetCrackerComponent gains networked `BerthLocalPos`, `BerthLocalRot` and `BerthSize`, written server-side whenever the berth resolves. The GRID entity is force-sent to any client who sees any chunk of it (RobustToolbox/Robust.Server/GameStates/PvsSystem.ToSendSet.cs:31-43, "Send the grid"), so these three fields reach every client aboard regardless of range — which is what makes the stage 9 radar ghost possible without a PVS override, since the radar has no BUI state to read.

D-O (NEW, from review). Projector firing state is RECONCILED every sweep, not written on edges.
 WFGravityProjectorSystem owns WFProjectorState and unconditionally overwrites it with no crack awareness: OnPowerChanged (WFGravityProjectorSystem.cs:70-76) sets Idle/Off on any PowerChangedEvent, OnRepaired (:87-95) sets Idle/Off after a repair. Those subscriptions are at :31 and :33 and F4 does not touch them. An APC brownout or a repair mid-crack would strand the projector at Idle for the rest of the cut, which blanks the emitter sprite layer (machines.yml:123-128 — Emitter is `visible: false` for Idle and Off, true only for Charging and Firing), kills the console beam pip and stops the diagram drawing beam lines, while the crack timer runs on. F4's 1 Hz sweep therefore calls `_projectors.SetState(ent, desired)` for every projector on the hull each pass, where desired = Firing while Cracking and not paused and no abort spin-down is running, Charging while paused, and otherwise leaves WFGravityProjectorSystem's own power/broken result alone. SetState is idempotent (:98-104 early-returns on no change). This is a display/effects reconciliation only: the grace timer already reads `Broken` and `_receiver.IsPowered` directly, never WFProjectorState, so the crack MECHANIC was never at risk — only everything the crew looks at.

=== 3. THE FALLING PUSH ===

`Fall(Entity<WFPlanetCrackerComponent> ent)` in WFCrackerSystem.Crack.cs, exact order:
  1. `ReleaseLock(ent)` — RemComp<ForceAnchorComponent>, RemComp<PreventGridAnchorChangesComponent>, `_shuttle.Enable(ent.Owner, force: true)`, then READ BACK PhysicsComponent.BodyType and Log.Error if still Static (D-M). This must precede the transit push: TryEnterTransit's own per-grid `_shuttle.Enable(gridUid)` at Transit.cs:490 is un-forced, so a grid still carrying PreventGridAnchorChanges stays Static for the whole fall (ShuttleSystem.cs:207-208 — wait, the un-forced guard is :205-206) with no error.
  2. Stop the centrifuge counting as lift: for every WFCentrifugeComponent on the hull that also has GravityGeneratorComponent, `_gravgen.WfSetGravityActive((uid, gravgen), false)`. UpdateGridGravity skips `!gravgen.GravityActive` when rebuilding _gravgenCapacity (Gravity.cs:65). Rejected alternatives: MaxHandledMass = 0 gives INFINITE lift (Gravity.cs:69 reads <= 0 as infinite, TryGetGravgenLoad:594 only < 0); cutting power takes 240 s (PowerChargeSystem.cs:152-155); WFGridAnchorLoadComponent.VirtualMass is rewritten every second by WFAnchorCapacitySystem.Update (:87-101).
  3. `EnsureComp<CEZGridFallerComponent>(cracker)`; `faller.Velocity = 0f`, `faller.GravityTime = _timing.CurTime`.
  4. `_zLevels.TryEnterTransit((cracker, mapGrid), startProgress: 1.0f)`; check the return and Log.Error on false (it returns false with no log when the map lacks CEZMapComponent or is already transit, Transit.cs:414-418).
  5. `SetState(ent, WFCrackState.Falling)` then raise `WFCrackerFallingEvent(cracker)` for F5's chunk at 0.98f (D-K).
  6. Stop every loop, PlayPvs the fall alarm.
 The automatic sweep never does any of this: it skips orbit layers (Gravity.cs:93-94, the WOLFGATE line) and Static bodies (:96-97). Expect up to 0.5 s of hover after step 2 (Gravity.cs:54-56 throttle vs :296 per-frame consult).

=== 4. CENTRIFUGE READING AND THE D25 HYSTERESIS ===

=== 5. CRACK AND GRACE TIMER MECHANICS ===

Both on WFPlanetCrackerComponent, both ticked by ONE 1 Hz sweep (0.25 s while Cracking) in WFCrackerSystem.Crack.cs, `_nextSweep` gate, the WFGravityAnchorSystem.cs:280-283 pattern.

CRACK TIMER
 Duration at begin: `BaseCrackTime * (d / ReferenceDistance) * meanMultiplier`, BaseCrackTime 12 min and ReferenceDistance 24 as [DataField]s, d from the now-public TryGetPairDistance, meanMultiplier = arithmetic mean of every healthy projector's CrackTimeMultiplier (D-B). Sets CrackEnd, CrackRemaining, CrackPaused = false.
 Pause: any tick where either targeted anchor has `Damaged == true` (WFGravityAnchorComponent.cs:34). Driven by WFAnchorDamagedEvent (fires both directions, Pairing.cs:130-131) AND re-checked in the sweep so a missed event cannot strand the timer. Falling edge into paused: CrackRemaining = CrackEnd - CurTime clamped >= 0. Rising edge out: CrackEnd = CurTime + CrackRemaining.
 Completion: `!CrackPaused && CurTime >= CrackEnd` -> SetState(Cracked) + WFCrackCompletedEvent(cracker, anchorA, anchorB, circleCentreXY, radius, groundMap). F4 extracts nothing.

GRACE TIMER
 Preconditions recomputed every sweep while Cracking or Cracked into a WFCrackFailure flags value on the component and in the BUI state:
   Centrifuge — no WFCentrifugeComponent on the hull, or !AtFull
   ProjectorsShort — fewer than RequiredProjectors (default 2) WFGravityProjectorComponents on the hull
   ProjectorPower — any projector with !_receiver.IsPowered(uid)
   ProjectorBroken — any projector with Broken (WFGravityProjectorComponent.cs:25)
 Read from Broken and IsPowered directly, never from WFProjectorState, which is why D-O is a display fix and not a mechanic fix.
 Suspended entirely during an abort spin-down.
 Rising edge: GraceRunning = true, GraceEnd = CurTime + GraceDuration (5 min), klaxon loop starts. Falling edge: GraceRunning = false, klaxon stops. Expiry: Fall().
 GraceEnd is a plain TimeSpan + [AutoPausedField] with a separate GraceRunning bool (the DrillEnd pattern), not a TimeSpan?.

ABORT SPIN-DOWN
 AbortEnd (TimeOffsetSerializer + AutoPausedField) and PendingAbort (WFCrackState?, networked). 30 s [DataField]. On expiry: ReleaseLock (with the D-M read-back), clear AnchorA/B and every timer, SetState(PendingAbort), PendingAbort = null.

PROJECTOR RECONCILIATION (D-O) runs in the same sweep, after the timers, so the desired state already reflects this tick's pause/abort status.

## CLOUD LAYER DECISION
DECISION UNCHANGED: DROP the cloud layer for crackable planets. In Resources/Prototypes/_WF/PlanetCracker/planets.yml, WFSurfaceAsclepiu changes `airLayers: 2` -> `airLayers: 3` (:6) and `cloudLayer: true` -> `cloudLayer: false` (:7), in one edit, landing in stage 2 with the PlanetNetworkTest adjustment. Reject the alternative of a _WF opt-out inside the renderer. One supporting COST figure is corrected below; the decision and its evidence stand.

EVIDENCE FOR THE PROBLEM
- ScalingViewport.RenderZLevels' downward walk terminates at the first CEZCloudLayerComponent: Content.Client/_CE/ZLevels/Core/ScalingViewport.CEZLevels.cs:185-190 sets occludeBelowDepth and breaks. WFSurfaceAsclepiu puts the cloud at depth 3 of a 0..4 stack (planets.yml:6-7). From orbit (depth 4) the walk adds exactly ONE pass, the cloud, then stops; plus the player's own map at :207, two passes total.
- Terminating the walk is only half of it. During the cloud's own pass cloudDeck is non-null (:324-326) and DrawCloudDeck(..., coverage 1f) at :377 paints an OPAQUE full-screen rect over everything already drawn. Patching only the walk break would be a silent no-op.
- WFCrackCircleOverlay filters on `xform.MapID != args.MapId` (Content.Client/_WF/PlanetCracker/Anchors/WFCrackCircleOverlay.cs:83-85,:98) and args.MapId is the current z-pass's map. No pass, no overlay. The crack site is currently invisible from the one place the crew spends the crack.

WHY DROPPING IT IS THE RIGHT LEVER
1. One YAML line pair, zero code cost. WFPlanetSurfacePrototype.CloudLayer already exists (Content.Shared/_WF/PlanetCracker/Planets/WFPlanetSurfacePrototype.cs:38-40) and WFPlanetNetworkSystem.BuildNetwork branches on it cleanly at :148-153 and :205-211. Nothing else in the codebase depends on a planet having a cloud layer.
2. The alternative costs THREE marked lines in a hot client render path, in _CE: the walk break (:185-190), the occludeBelowDepth/occludeBand assignment that also drives the transit-pass cull, and the opaque deck fill (:324-326 -> :377). Three lines in a hot render path to buy what one data field already buys is a bad trade, and the failure mode is invisible (overlay exceptions go to the clyde.overlay sawmill, Clyde.HLR.cs:163-167).
3. The cost is CLIENT RENDER ONLY, not bandwidth and not biome generation. CEZLevelsSystem.UpdateViewer spawns a CEZLevelEye for every level i = 1..MaxZLevelsBelowRendering with no cloud or ground check (Content.Server/_CE/ZLevels/Core/CEZLevelsSystem.View.cs:170-177) and that bound is a hard-coded 10 (CESharedZLevelsSystem.Constants.cs:10). An orbiting client already replicates all four layers below it today; the cloud saves draw calls, never a byte.
4. What the crew will see: the ground renders at ZLevelViewShrink^4 = 0.85^4 = 0.52 scale, offset ZLevelOffset * 4 along the inverse eye rotation, under the cumulative CEZLevelBlurOverlay — a 3x3 box blur at 2 px radius plus a 30% tint toward the map ambient (Resources/Textures/_CE/Shaders/zblur.swsl:6-7,:13-23). Asclepiu's air ambient is #c8fdff (planets.yml:29), near white, so the tint is negligible. A 20-44 tile crack circle at 52% scale is comfortably legible. Ten layers are allowed; the walk is nowhere near its bound.

CORRECTION FROM REVIEW (accepted): the added render cost is FOUR passes, not three. With airLayers 3 the walk from orbit adds a pass for air at relative depths -1, -2 and -3 and then one for the ground layer, which is the first CEZGroundLayerComponent and so sets occludeBelowDepth and breaks (ScalingViewport.CEZLevels.cs:192-196; groundComponents carries CEZGroundLayer at planets.yml:24-26). Four passes, four TryFindEmptyTiles scans and four cumulative blur applications. This changes the magnitude of the frame-time risk, not the decision: the walk's own bound is ten.

WHY airLayers MUST GO 2 -> 3 IN THE SAME EDIT
The cloud layer is not only a cloud: cloudComponents (planets.yml:33-39) carries MapLight #c8fdff and an inherent Gravity, identical to airComponents (:27-32). It functions as a third gravity-bearing air layer. Dropping it alone shortens the stack from five maps to four, moves orbit from depth 4 to depth 3, removes one level of fall, and shifts every touchdown number keyed to the five-level stack. Raising airLayers to 3 preserves depth count, orbit depth, fall duration and CrashGrid timings exactly, and WFPlanetNetworkSystem.cs:197-203 already stamps airComponents onto layers 1..AirLayers, so layer 3 gets the MapLight and Gravity the cloud was providing.

WHY DECIDE IT IN F4 RATHER THAN DEFERRING TO F5
F4's own mechanics do not need it — the console diagram is the authoritative readout and F4 ships no beams or ring decals. But PlanetNetworkTest asserts the stack shape (LayerCount 5 at :45, per-depth assertions at :72-85, AtmosphereIsPerLayer over layers 0-2 and orbit at :138-146) and its layer-role comment at :44 names the cloud. Changing the stack in F5 means touching those tests twice. Deciding now costs one extra assertion and a comment fix.

- PlanetNetworkTest.cs: correct the layer-role comment at :44 to "0 ground, 1-3 air, 4 orbit"; extend AtmosphereIsPerLayer to assert layer 3 is not space; add an assertion in BuildsTheFullStack that no layer carries CEZCloudLayerComponent. ## OPEN RISKS
- CEZGridSyncSystem.OnGridMoved (Content.Server/_CE/ZLevels/Core/CEZGridSyncSystem.cs:119-155) silently reverts or propagates any grid transform move when the cracker is in a CE grid network of two or more grids. Neither the design nor the F1F3 plan mentions this system. The plan refuses the snap in that case, but the refusal is only as good as TryGetGridNetwork: if a connector links the cracker between the check and the move, the snap is undone in the same tick and the state machine advances anyway. CrackConsoleTest.SnapIsRefusedInAGridNetwork covers the known case; a mid-tick link is not covered.
- The corrected colour-space rule (D-I) still leaves one unavoidable inconsistency: DrawLine, unfilled DrawCircle and DrawRect need Color.FromSrgb while DrawString must take the raw colour to match adjacent stock Labels, so a diagram's text and its lines drawn from the same skin token are different shades. There is no fix without re-deriving how the glyph atlas shader consumes Modulate. Stage 6's gate asks for a line/ring/Label A-B; if they disagree the fix is in WFDiagramControl alone. Note this risk is now about TEXT only — the previous revision's rule also got unfilled circles wrong, which would have made every dial ring and anchor mark visibly lighter than the shipped world overlay.
- PowerChargeSystem.OnAnchorStateChange (:35-43) still zeroes Charge and Active on any unanchor cause other than the wrench — an explosion, a grid split — with no cancellation hook; `Anchorable: flags: None` (machines.yml:37-38) blocks only the tool path. During Cracking that silently arms the grace timer with a falling spin dial as the only cue, and 240 s later the ship drops. F4 does not fix it.
- _gravgenCapacity is rebuilt only inside UpdateGridGravity's 0.5 s throttle (Gravity.cs:54-56) while HasPooledGravgenSupport is consulted every frame from IntegrateFallingGrid (:296), so clearing GravityActive in the Falling push takes up to half a second to bite. The plan zeroes faller.Velocity and pulls GravityTime forward to make the drop crisp anyway, but the half second is not eliminable from content.
- The crack site is invisible from orbit today and the cloud-layer change is the fix, but not a complete one: TryFindEmptyTiles (ScalingViewport.CEZLevels.cs:40-92) resolves a single grid at the screen's bottom-left corner (:74) and gates the whole downward walk on it, so a pilot inside a sealed control room sees nothing below regardless of the cloud setting, and the view can flip as they pan. The console site diagram remains the authoritative readout; the z-view is decoration.
- CORRECTED COST FIGURE: dropping the cloud layer moves render cost onto every orbiting client, and it is FOUR added passes, not three — from orbit the walk adds air-3, air-2, air-1 and then ground, which sets occludeBelowDepth and breaks (ScalingViewport.CEZLevels.cs:178-204) — so four TryFindEmptyTiles tile scans, four cumulative CEZLevelBlurOverlay applications, and four WFCrackCircleOverlay redraws. PVS and biome generation are unchanged (CEZLevelEyes already descend ten levels with no cloud check, View.cs:170-177), so this is frame time only, but it is new frame time that will be misattributed to the crack feature rather than to the layer change.
- The part-multiplier mean (D-B) is an invention: the design says only 'part multiplier' for two projectors. BOTH the mean and the minimum reproduce §5's stated 5.6-to-20-minute range exactly, because §5 quotes those endpoints only for uniform part tiers; only the product is excluded by the numbers (0.49 undershoots the 5.6 min floor). The mean is chosen so a single-projector upgrade is worth something. If balance later wants 'worse of the two', the formula and CrackTimerTest.PartMultiplierIsTheMeanOfBothProjectors change together.
- ASSET_REQUIREMENTS' 'Centrifuge spin loop — pitch is shifted in code with spin' is not implementable: AudioComponent is [Access(typeof(SharedAudioSystem))] with Other=Read and SharedAudioSystem exposes SetGain and SetPlaybackPosition but no SetPitch. The rotor dial gives the visual speed cue instead.
- SharedGravitySystem.StartGridShake hard-codes ShakeTimes = 10 at 0.2 s (Shake.cs:64) with no intensity or duration parameter, so 'repeating shake for the whole crack' is a 2 s re-trigger loop, and the client only shakes players whose own xform is on that grid (Content.Client/Gravity/GravitySystem.Shake.cs:26-32,:52-56). Crew who later stand on the chunk will feel nothing from the hull's shake; F5 must raise the effect on both grids.
- The clear-area check only looks at grids. Entities parented to the map inside the swept 8-tile path — a drifting crate, a spaced body, a player in EVA — are not detected and will be overlapped by the snapped hull with no crush. Left to F5's chunk placement; if it bites in playtest the fix is one GetEntitiesIntersecting call in TrySnapToCircle.
- WFCentrifuge maxHandledMass 3000 and the D11 numbers are placeholders tuned to code-built test hulls with no real map behind them; the console's load bar reports against a made-up capacity until the cracker vessel exists. The machines.yml:50-51 asymmetry stands: Gravity.cs:69 reads <= 0 as infinite lift while TryGetGravgenLoad:594 reads only < 0 that way.
- Design D23 plus the 'no abort' structure means any bug in the begin-crack precondition chain is unrecoverable in-round: the only exits from Cracking are completion, anchor loss and the fall. The admin `wfcracker state` subcommand is the sole escape hatch, which is why it is in scope rather than deferred.
- Overlay and Control draw exceptions behave differently: Overlay exceptions are swallowed into the 'clyde.overlay' sawmill (Clyde.HLR.cs:163-167) while a Control's surface in the client log. THREE of the four blockers this review caught (unregistered shared system, uninjected dependencies, PVS-missing entities) are Draw-time or draw-silent failures that compile clean and pass every headless gate, which is why stage 6's smoke step and stage 8's manual pass are now non-optional rather than 'offer the harness and skip'.
- Two channels now carry spin/load (BUI state for the console, networked component for the machine window, D-D2). They are written in the same place by the same system and the machine window is only openable in PVS range, so they cannot disagree in practice — but a future reader may see the duplication as an oversight and delete one. The class summaries on WFCentrifugeComponent and WFCrackConsoleState both say why both exist.
- The berth marker parents MarkerBase, so it stays invisible and unclickable to ordinary players, AND is routinely outside PVS. After F4 the console diagram is the only in-round indication of where the chunk will hang; if the optional stage 9 radar ghost is dropped, a pilot away from the console has none at all.
