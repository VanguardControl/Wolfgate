 [R2] The system keeps THREE scratch collections, not two, and they have distinct jobs: `_seen` (HashSet<Vector2i>) is the per-event dedupe across overlapping AABBs and accumulates EVERY index walked, scar member or not; `_matched` (List<Vector2i>) holds only the indices that passed the membership test; `_buffer` (List<(Vector2i, Tile)>) is the SetTiles payload. E-C. THE ORDER IS SetState(Disconnecting) FIRST, ALWAYS — AND THE SPIN-DOWN MUST BE CLEARED BY HAND. While `State == Cracked` the sweep calls `StartAbort(ent, AnchorsPlaced)` the instant `TryGetTargetedPair` fails (WFCrackerSystem.Crack.cs:90-93), and 30 s later `FinishAbort` does ReleaseLock + ClearTarget + SetState(AnchorsPlaced) (:335-361), which `ReconcilePair` then demotes to Surveying (StateMachine.cs:168-172). `StartAbort` early-returns outside `Cracking or Cracked` (:317-318), so leaving Cracked makes STARTING an abort inert, and no later F7 step can be mistaken for one. `ClearTarget` at Released entry makes `IsTargeted` false before the anchors terminate (StateMachine.cs:197-201, read by OnAnchorBroken :118 and OnAnchorDestroyed :127).
 [R2] That is only half the story and revision 1 was wrong to stop there. `StartAbort` (Crack.cs:315-332) sets `PendingAbort`/`AbortEnd` but NEVER changes `State`, so a hull spinning down an abort is still `Cracked`; and the sweep's `if (ent.Comp.PendingAbort is not null)` arm (Crack.cs:79-84) is the FIRST arm of the chain and is not gated on state, so any `else if` added later is unreachable while a spin-down is pending. `ForceSwitchOff` (Anchors/WFGravityAnchorSystem.Control.cs:33-43) skips the cancellable attempt entirely but still raises `WFAnchorSwitchedOffEvent`, and `wfcracker disconnect` calls it on both anchors in one tick (WFCrackerCommand.cs:177-193) — so without a second gate the admin path could enter Disconnecting mid-spin-down, the evacuation would never tick, both alarm loops would run forever, and `FinishAbort` (which has no state guard) would 30 s later overwrite Disconnecting with AnchorsPlaced. Two defences, both required:
   - `OnSwitchedOff` refuses while `PendingAbort is not null`, mirroring veto guard 3, so the ForceSwitchOff path is gated too;
   - `EnterDisconnecting` clears `PendingAbort = null; AbortEnd = TimeSpan.Zero;` before `SetState`, so the chain's first arm is provably false for the whole of Disconnecting and Released. Nothing else in the tree writes `PendingAbort` except `StartAbort`, which cannot run outside Cracking/Cracked.
 With both in place the new arms may stay as `else if` after the abort arm; no hoist and no upstream-shaped edit to `FinishAbort` is needed.

E-H. THE TWO SYSTEMS NEVER TAKE A [Dependency] ON EACH OTHER; THE HANDOFF IS BROADCAST EVENTS. `WFPlanetChunkSystem` already depends on `WFCrackerSystem` (WFPlanetChunkSystem.cs:46), so the reverse would be a cycle. F7 copies F5's own pattern (`Fall` raises `WFCrackerFallingEvent` at Crack.cs:410-411, the chunk system subscribes it at WFPlanetChunkSystem.cs:64 and calls DropChunk):
 - hull -> chunk: new `WFCrackerReleasingEvent(EntityUid Cracker)` raised on evacuation expiry; the chunk system subscribes it and calls `DropChunk`.
 - hull -> chunk (alarm arming): the chunk system subscribes the EXISTING `WFCrackStateChangedEvent` (broadcast, by ref) and starts its evacuation alarm on the Disconnecting edge. Because the handler reads `EvacEnd` off the cracker component, `EnterDisconnecting` writes every timer field BEFORE calling `SetState`.
 - chunk -> hull: the EXISTING `WFChunkDroppedEvent` (WFChunkEvents.cs:16, no production subscriber) is subscribed by the cracker side and drives Disconnecting -> Released. It carries `EntityUid.Invalid` when the back-link no longer resolves (WFPlanetChunkSystem.cs:243-245), so the handler tolerates an invalid uid and returns.
 [R2] The STOP edge cannot ride `WFCrackStateChangedEvent`. `DropChunk` nulls the hull's back-link (`crackerComp.Chunk = null`, WFPlanetChunkSystem.cs:229-236) BEFORE it raises `WFChunkDroppedEvent` at :243-246, and that event is what drives `EnterReleased` -> `SetState(Released)`. By the time the Disconnecting->Released change reaches the chunk handler, `TryGetChunk` (:251-263) returns false, so a stop keyed on `TryGetChunk` is dead code on the normal path. The chunk alarm is therefore stopped from exactly two places that are always reachable: `OnLanded` (the normal end) and an `Old == Disconnecting` escape branch that resolves the chunk by QUERYING `WFPlanetChunkComponent` for one whose `Cracker` net-entity is this hull and whose `Dropped` is false — the only case that branch has to cover is an admin `wfcracker state` pulling the hull out of Disconnecting before any drop happened.

E-I. [R2 — SUBSTANTIALLY REVISED] CRASH INTENSITY IS PURELY THE PER-GRID FALLER TUNABLES; THERE IS NO SEPARATE F7 CENTRAL BLAST. Revision 1 proposed suppressing the engine's mis-centred central blast and re-queueing an equivalent one at the crater from `OnLanded`. The re-queue is unsound and is DROPPED. Evidence:
 - `QueueExplosion` merges any incoming explosion of the same prototype within `MaxCombineDistance` of a still-queued one by ADDING `TotalIntensity` only; the incoming `slope` and `maxTileIntensity` are discarded and the call returns (ExplosionSystem.cs:386-400). `Default` does not override `MaxCombineDistance`, which is `1f` (Content.Shared/Explosion/ExplosionPrototype.cs:91; Resources/Prototypes/explosion.yml:3-17).
 - Entries leave `_queuedExplosions` only when dequeued for processing, one explosion at a time under the TilesPerTick / MaxProcessingTime throttle (ExplosionSystem.Processing.cs:53, :95-107), so the hundreds of per-tile crash entries CrashGrid queued (Gravity.cs:409-421) are still resident seconds later, on the same map as the ground grid so `EntityCoordinates.TryDistance` resolves. The chunk sweep is 1 Hz (WFPlanetChunkSystem.cs:126-129), so `OnLanded` runs up to a second after CrashGrid, well inside that window.
 A blast queued at `HoleCentre` would therefore be absorbed into whichever per-tile entry is within one tile of it, contributing intensity under slope 2 / maxTileIntensity 2 — i.e. it would be exactly equivalent to raising `CrashTileIntensity`, which is a DataField we already control. So F7 states the equivalence and keeps only the tunables:
   faller.CrashIntensityPerTile = 0f   // the engine's own central blast, suppressed
   faller.CrashTileIntensity    = comp.CrashTileIntensity    (default 4f, engine default 12f)
   faller.CrashTileMaxIntensity = comp.CrashTileMaxIntensity (default 2f, engine default 4f)
 `CrashIntensityPerTile = 0f` is still correct and still worth doing, for the reason revision 1 found: `CrashGrid` queues that one through the `EntityUid` overload, which resolves the epicentre via `TryGetMapOrGridCoordinates(uid, ...)` (ExplosionSystem.cs:295-320, :312) = the chunk GRID's origin, and `TryExtract` sets the chunk grid's origin to the GROUND GRID's origin so tile indices match (Extraction.cs:141-142). On a real biome planet the cut circle is hundreds of tiles from (0,0), so that blast detonates somewhere else entirely; the fixture's circle centre is (8, 0.5) against a ground origin of (0,0), which is why no shipped test could catch it. Zero makes it a no-op through the `totalIntensity <= 0` early return (ExplosionSystem.cs:374). The per-tile blasts are already at chunk-tile coordinates directly over the crater, so the crash needs no relocation.
 The three `Centre*` DataFields, the `_explosion` dependency on the chunk system and the `DropWritesTheCentralBlast` assertions from revision 1 are all removed.
 CONSEQUENCE FOR RIM DECALS, stated honestly: because merging accumulates `TotalIntensity` into a handful of entries while `MaxTileIntensity` caps per-tile intensity, the merged crash footprint is roughly `TileCount * CrashTileIntensity / CrashTileMaxIntensity` tiles — about 2x the disc area at the defaults, i.e. ~1.41R — so rim tiles ARE inside it. At `CrashTileMaxIntensity = 2` the Default prototype's `TileBreakChance` interpolates to ~0.1 per tile (tileBreakChance [0, 0.5, 1] over tileBreakIntensity [0, 10, 30], linear, ExplosionPrototype.cs:126-139), and `DecalSystem.OnTileChanged` deletes any decal on a tile that becomes space (DecalSystem.cs:165-177). So rim-decal survival is probabilistic in production and must not be asserted against a live crash. Every test that lands a chunk uses `SoftenCrash`, which zeroes `CrashTileIntensity` and suppresses the tile blasts entirely through the same `totalIntensity <= 0` early return, making the landing geometry deterministic.
 `GridCrashVelocity` is left at 0.35 (CEZGridFallerComponent.cs:62): impact after the 4-level fall from depth 4 with GridGravity 0.15 / seed 0.3 / terminal 1.2 is ~1.1 lvl/s, three times the threshold.

E-J. THE CHUNK IS ALREADY OVER ITS OWN HOLE WHEN IT LANDS; F7 ONLY RE-ASSERTS THE POSE AND FREEZES THE WRECK. The descent stops at depth 0 because `SetTransitAltitude`'s `while (progress < 0f)` loop calls `ConvoyBlockedByPlane(convoy[0], bottomLower)` (Transit.cs:564-571 -> :645-657 -> `HasGroundUnderFootprint`, Gravity.cs:629-643), which tests the grid's whole SQUARE world AABB against the ground layer's tiles — the disc's `Tile.Empty` interior is irrelevant, the rim overhang catches it. World XY is preserved end to end (`MoveGridSetToMap` re-parents by world position, Transit.cs:766-819). So no placement maths is needed. F7 adds only:
   - a pose snapshot in DropChunk (`DropWorldPos`/`DropWorldRot` from `GetWorldPositionRotation` before `TryEnterTransit`) and a one-shot `SetWorldPositionRotation` back to it at landing, because the chunk is DYNAMIC for the whole fall (`TryEnterTransit` calls an UN-FORCED `_shuttle.Enable`, Transit.cs:490) and nothing re-disables it;
   - `_shuttle.Disable(chunk, force: true)` + `EnsureComp<PreventGridAnchorChangesComponent>` at landing, which also stops the CE fall sweep ever looking at the wreck again (it skips static bodies) and stops ground friction / wall collision sliding it off the crater.

E-K. DELETION USES THE UNPARENT PRECEDENT, NOT A BARE QueueDel. `QueueDel` of a grid recursively deletes every child, so a bare delete silently removes any player still aboard, with no body and no admin log. [R2 — CITATION CORRECTED] The precedent is `LinkedLifecycleGridSystem.UnparentPlayersFromGrid(grid, deleteGrid: true, ignoreLifeStage: false)` at Content.Server/_NF/StationEvents/EventSystems/LinkedLifecycleGridSystem.cs:178-206 — revision 1 cited `Content.Server/StationEvents/Events/LinkedLifecycleGridSystem.cs`, which does not exist. The NAMESPACE, however, is `Content.Server.StationEvents.Events` (declared at that file's line 15), NOT `Content.Server._NF.StationEvents.EventSystems`; the `using` stage D writes is the former. The method detaches minded mobs (resolving riders to their vehicle/mech and dragging pulled entities), deletes the grid, then restores each survivor at its own saved WORLD position — for a wreck plugging its own crater, the crater floor on the ground layer. It deletes with `Del(grid)` at :195, i.e. SYNCHRONOUSLY, which is why `Cleanup` may only ever be called from the post-enumeration `_cleanupBuffer` drain and never from inside the chunk query loop. Nothing else deletes the wreck: `GridCleanupSystem` refuses a grid parented to a map grid and a grid with `CleanupImmuneComponent`, and `ParkChunk` added exactly that (Extraction.cs:433).

E-L. THE CLEANUP IS A DELAYED SECOND PASS, NOT PART OF THE LANDING, AND IT APPLIES TO EVERY LANDED CHUNK. The crash explosions are queued synchronously inside `IntegrateFallingGrid` but drained over many ticks, and they are anchored to `EntityCoordinates` parented to the CHUNK GRID — deleting it early would void them. `CleanupDelay` defaults to 10 s.
 [R2] Revision 1 left it implicit that `UpdateDropped` arms the cleanup for EVERY dropped chunk, which generalises grid deletion beyond the release path onto the F4 hull-fall drop (`OnCrackerFalling`, WFPlanetChunkSystem.cs:110-119) and the D24 watchdog drop. That generalisation is now the STATED decision rather than an accident: a chunk that has crashed into a planet is a wreck whichever path dropped it, the three paths differ only in why, and a per-path flag would leave two of them littering permanently-immune grids on the ground layer for the rest of the round. It is pinned by its own test (`TheHullFallDropIsAlsoCleanedUp`) so the behaviour cannot regress silently. Sequence at cleanup: capture `GroundMap`, `UnparentPlayersFromGrid(chunk, true)`, then `_scars.ReStamp(groundMap)` — driven off the ground-grid scar, so it works after the chunk component is gone.

E-M. NO NEW PROTOTYPES, NO NEW ART, NO PER-PLAYER ALERT. The brief allows a per-player alert "if cheap"; it is not. `AlertsComponent` is `SendOnlyToOwner` and exists only on player-controlled entities, so an alert needs a new `- type: alert` prototype WITH an icon sprite, a locale pair, a per-sweep enumeration of the grid filter, and a tracked shown-set with `ClearAlert` on leave/abort/expiry. F7 instead uses a looping alarm on each grid, one filtered announcement per grid, and `PopupType.LargeCaution` popups on the discrete beats. [R2] This also disposes of the obvious fix for the explosion-merge problem in E-I — an `_WF` clone of `Default` with `maxCombineDistance: 0` — which would have been a new prototype; the merge is instead accommodated rather than fought.

E-N. [R2 — CITATION CORRECTED] ALARM AUDIO IS `PlayGlobal` TO A GRID FILTER, RE-ISSUED ON A CADENCE. `PlayPvs` on a GRID parents the audio at the grid's local (0,0) with `AudioParams.Default.MaxDistance` = 15 tiles, so F4's existing hull klaxon is a bridge-area klaxon; copying it would ship a silent evacuation alarm on a capital hull. F7 takes the announce-then-`PlayGlobal` SHAPE from `GridPowerSystem.Announce` (Content.Server/_WF/Administration/Systems/GridPowerSystem.cs:147-166) — revision 1 said "verbatim", which is wrong in two details: that precedent builds its filter with `Filter.Empty().AddWhere(session => session.AttachedEntity is { } entity && Transform(entity).GridUid is { } onGrid && grids.Contains(onGrid))` and passes NO `colorOverride`. F7 substitutes `Filter.Empty().AddInGrid(grid, EntityManager)` (RobustToolbox/Robust.Shared/Player/Filter.cs:140, which is what `AddWhere` there is hand-rolling) and adds `colorOverride: Color.Red`; `playSound: false` plus a separate `_audio.PlayGlobal(sound, filter, true, AudioParams.Default.WithLoop(true).WithVolume(-4f))` is the part taken unchanged. Because `PlayGlobal` FREEZES its recipient set at play time, the loop is stopped and replayed every `EvacReissue` (15 s) so a latecomer boarding mid-countdown still hears it. Popups are anchored on EACH RECIPIENT'S OWN entity (`PopupEntity(msg, playerEnt, playerEnt, LargeCaution)`) because the client silently drops a popup whose anchor is outside its PVS.
 [R2] `DispatchFilteredAnnouncement` takes a PRE-FORMATTED string (`(Filter filter, string message, EntityUid? source = null, string? sender = null, bool playSound = true, SoundSpecifier? announcementSound = null, Color? colorOverride = null)`, Content.Server/Chat/Systems/ChatSystem.cs:388-395), and half the F7 locale keys carry a `{ $seconds }` variable. Both helpers therefore take arguments: `Announce(EntityUid grid, string key, params (string, object)[] args)` and `PopupOnGrid(EntityUid grid, string key, params (string, object)[] args)`, each doing the `Loc.GetString(key, args)` itself. Revision 1 declared them key-only and then called a differently-named three-arg `PopupOnGrids`; that mismatch would have shipped literal `{ $seconds }` in the announcements.

E-O. THE CHUNK'S `DropStream` IS A LEAK AND F7 FIXES IT. `DropChunk` starts a looped `PlayPvs` (WFPlanetChunkSystem.cs:238) and the watchdog sweep then skips the chunk forever (`if (comp.Dropped) continue;`, :136-137). E-P. ## OPEN RISKS
- [R2] The crash is now only the per-tile blasts, and because QueueExplosion merges same-prototype explosions within one tile by adding TotalIntensity while MaxTileIntensity caps per-tile output (ExplosionSystem.cs:386-400), the merged footprint is roughly TileCount * CrashTileIntensity / CrashTileMaxIntensity tiles — about twice the disc's area at the defaults, i.e. ~1.41R. Rim tiles are inside it, the Default prototype's TileBreakChance interpolates to ~0.1 per tile at intensity 2 (ExplosionPrototype.cs:126-139), and DecalSystem deletes decals on tiles that become space (DecalSystem.cs:165-177). So the rim decal ring is probabilistic in production; the tests assert it only under SoftenCrash. Tuning CrashTileMaxIntensity below ~1 would make breakage negligible but also make the crash visually nothing.
- [R2] DropChunk writes CrashIntensityPerTile = 0 on EVERY drop, including the F4 hull-fall path (OnCrackerFalling, WFPlanetChunkSystem.cs:110-119) and the watchdog path, and no replacement central blast is queued anywhere. The chunk crash is therefore quieter than an ordinary CE grid crash by design; if playtesting wants a bigger bang the only correct lever is CrashTileIntensity, not a second QueueExplosion.
- [R2] The cleanup now deletes the wreck on all three drop paths, not just the release path. That is intentional and tested, but it means a hull that simply falls with a parked chunk loses that chunk permanently 10 s after impact, which no design section states.
- Smimsh's Frontier guard (`if (xform.MapID == _ticker.DefaultMap) break;`, ShuttleSystem.FasterThanLight.cs:1406) silently skips the whole crush and ReserveTiles loop on the ticker's default map. The fixture builds its own ground map so TheHoleSurvivesTheLanding is meaningful there, but a future fixture change putting the ground layer on the default map would make it pass vacuously. ScarIsRecordedAtExtraction is the paired non-vacuity check.
- The scar is recorded from WFChunkExtractedEvent, so a chunk cut before this feature ships (a saved map, a `wfcracker extract` in an already-running round) has no scar and its hole is unprotected. There is no back-fill and no admin command to add or clear a scar.
- WFCrackScarComponent lives on the ground grid, which WFPlanetNetworkSystem can delete and rebuild (F0). A rebuilt network loses every scar; the planet stays flagged Cracked on the sector body, so the crater reverts to intact terrain with no way to re-cut it.
- The Released -> Idle transition is gated on a ReleaseSettle timer plus a `Locked || HasComp<ForceAnchorComponent>` check. A hull force-anchored by a mapper sticks in Released forever. That is deliberate — it surfaces the D-M failure — and the error is now logged once rather than at 1 Hz, which means a server that misses the first line has no further signal.
- Entering Disconnecting permanently disarms the grace timer, so a centrifuge or projector failure during the 60 s evacuation no longer drops the hull. This is a deliberate reading of design §3 but a rule the design never states either way.
- PlayGlobal freezes its recipient set, so the alarm is re-issued every 15 s. A player boarding at second 59 hears nothing, and every re-issue restarts the loop from its first sample rather than crossfading.
- The per-tile crash blasts still queue one QueueExplosion per non-empty chunk tile inside one synchronous pass (Gravity.cs:409-421): ~314 for the fixture disc, ~1520 at the design's mid-size cut and ~6100 at the 44-tile diameter, each doing an O(queued) combine scan. The intensity cut reduces the drain, not the queueing spike. Nothing in this plan measures that spike.
- Cleanup uses a fixed 10 s delay rather than waiting for the explosion queue to drain, because ExplosionSystem exposes no queue-empty predicate. A very large disc on a loaded server could still be detonating when the grid is deleted, voiding the remaining blasts (their EntityCoordinates are parented to the chunk grid).
- UnparentPlayersFromGrid restores survivors at their own world position, which for a wreck plugging its crater is a Tile.Empty hole on the ground layer. A player restored onto an empty tile is treated as standing over nothing by the CE z-movement ground test (CESharedZLevelsSystem.Movement.cs:318) and may fall again. Not exercised by any test here.
- Nothing ejects or gibs a non-minded mob, an item or a crate on the chunk: UnparentPlayersFromGrid only collects humanoids, borgs and occupied mind containers, so everything else is deleted with the grid. Mined ore left on the chunk is destroyed silently.
- WFAnchorCapacitySystem.TryGetCarrier (WFAnchorCapacitySystem.cs:267) excludes only anchored entities and WFPlanetLayerComponent grids, so an UNANCHORED anchor or crate left loose on the chunk is tallied against the chunk grid and written into WFGridAnchorLoadComponent.VirtualMass, which the CE pooled-lift check reads during the drop.
- The pairing-window countdown is visible only on the crack console and through three popups near the anchors. The anchor examine line was deliberately not added because <WFGravityAnchorComponent, ExaminedEvent> is already claimed (WFGravityAnchorSystem.cs:59).
- [R2] The chunk alarm's only reliable stop is OnLanded; the state-change escape branch covers just the admin `wfcracker state` case and resolves its chunk by a component query because the hull's back-link is already nulled by then (WFPlanetChunkSystem.cs:229-236). If a future change drops a chunk without ever landing it — deleted mid-transit, or a transit map torn down — nothing stops the loop, though the audio entity dies with the grid.
- ShuttleFlattenEvent fires for every Smimsh anywhere in the round. The scar handler's early-out is one TryComp per event, but on a planet with many scars the AABB walk is O(tiles in AABB * scars); no cap is applied and the scar list never shrinks.
