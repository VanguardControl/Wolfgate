# F5 engine research (read-only API maps, 2026-09-13)

Four Opus readers mapped the engine, _CE, upstream and committed _WF code for F5 (extraction, beams, chunk, effects) while F4 was being implemented. Line numbers are from that checkout; verify before relying on them.

## Extraction: reading the disc, the new grid, the hole, decals

### Summary

API map for F5 disc extraction. Verified against engine (RobustToolbox), _CE z-levels, upstream biome/decal/salvage code and committed F0/F1/F3 _WF code in worktree .claude/worktrees/modest-chaum-01364c. Key findings: (1) reading a disc needs GetLocalTilesEnumerator with ignoreEmpty:false because GetTileRef fabricates Tile.Empty for missing chunks and every tile-intersecting helper defaults to ignoreEmpty:true; (2) BiomeSystem has NO TileChangedEvent subscriber, so nothing records SetTiles into ModifiedTiles — the hole must be pinned explicitly, and BiomeComponent is [Access(typeof(SharedBiomeSystem))] so that needs a _WF partial of the sealed BiomeSystem (precedent CEZLevelsSystem.WFVirtualMass.cs); (3) BiomeSystem.Preload queues MARKER chunks only and generates no tiles — ReserveTiles is the only call that forces terrain to exist; (4) SetTiles raises exactly one TileChangedEvent for the whole batch, so a 1520-tile disc costs one CE connector re-flood, one atmos/navmap/pathfinding/decal pass, but CESharedZLevelsSystem.Movement.OnTileChanged does one lookup query per changed tile; (5) GridFixtureSystem's split is the exact precedent for create-grid → match pose → one SetTiles → ReAnchor anchored → SetParent unanchored → one SetTiles(Tile.Empty) on the source, in that order; (6) SharedTransformSystem.ReAnchor is internal and asserts same MapID, so a cross-map chunk needs Unanchor+reparent+AnchorEntity; (7) moving anything across maps runs SharedPhysicsSystem.HandleMapChange → RecursiveMapUpdate → ClearJoints on the whole subtree, silently dropping pull joints and dock welds; (8) CE ground detection is purely !Tile.IsEmpty, so only Tile.Empty lets mobs and the chunk fall into the hole — and Tile.Empty makes TryAddDecal refuse and DecalSystem.OnTileChanged wipe decals there, so ring/rim decals belong on the non-empty rim; (9) a chasm-variant hole is wrong: chasm is an anchored entity whose ChasmSystem QueueDels the tripper and _CE has zero chasm integration (the two `using Content.Shared.Chasm` lines in _CE are unused); (10) IMapManager.CreateGridEntity leaves the grid un-map-initialised and fires GridAddEvent while still in nullspace, and the follow-up AttachParent happens pre-init so SetCoordinates returns before RaiseMoveEvent — therefore CEZLevelsSystem.RefreshGridZPhysics never runs for a grid created directly on the orbit map, and SweepMapGridsForZPhysics (its only bulk fallback) has no callers; re-parenting the finished grid onto the orbit map with SetCoordinates is what fires EntParentChangedMessage and grants CEZPhysics+CEZGridFaller. F0's orbit exemption is keyed on WFOrbitLayerComponent on the MAP, so the chunk inherits it with no marker of its own.

### Recommendations

EXTRACTION ORDER (lifted from GridFixtureSystem.cs:265-357, adapted for a cross-map destination):

1. GEOMETRY. radius = SharedWFGravityAnchorSystem.GetCutRadius(pairDistance, padding) (SharedWFGravityAnchorSystem.cs:7); centre is the midpoint of the two anchor centres in the ground map's frame. Ground map: GridUid == MapUid at identity transform (F1F3 A.3), so local == world and no matrix work is needed.

2. FORCE THE TERRAIN TO EXIST. Do NOT call Preload — it only queues marker chunks (BiomeSystem.PlanetSetup.cs:152). Call ReserveTiles(groundMap, circleAabb.Enlarged(1f), reusableList) after Clearing the list (BiomeSystem.PlanetSetup.cs:76; precedent WFPlanetNetworkSystem.cs:136-138). That both generates every missing tile and adds the indices to BiomeComponent.ModifiedTiles, which is what stops the biome regenerating over the hole (BiomeSystem.ChunkLoader.cs:40-41, :85, :281). Take the AABB, not the circle, so all four corner chunks are pinned; the extra corner tiles cost nothing and stop a half-pinned 8x8 chunk. Then verify: re-read the disc and log any tile still IsEmpty — ReserveTiles silently skips tiles with no matching biome layer (BiomeSystem.PlanetSetup.cs:95-98).

3. READ THE DISC. GetLocalTilesEnumerator(groundMap, groundGrid, circleAabb, ignoreEmpty: false) (SharedMapSystem.Grid.cs:889) and radius-test `tileRef.GridIndices + grid.TileSizeHalfVector` yourself. ignoreEmpty:false is mandatory — the default true drops every unloaded tile (SharedMapSystem.Grid.cs:1726-1735) and a fabricated Tile.Empty is indistinguishable from real space (:744-749). Copy the whole Tile struct; never rebuild it from TypeId, because Variant and RotationMirroring carry the biome's look (Tile.cs:28, :33) and Tile.WithVariant drops RotationMirroring (:141).

4. CREATE THE CHUNK GRID ON THE GROUND MAP FIRST, not on orbit. _mapManager.CreateGridEntity(groundMapId), then SetWorldPositionRotation to the ground map's own pose (GridFixtureSystem.cs:271) so tile indices are identical on both grids and no coordinate conversion is needed anywhere. GridInitializeEvent fires (SharedMapSystem.Grid.cs:527) so DecalGridComponent lands automatically; SharedPhysicsSystem.OnGridAdd gives it Physics+Fixtures+Static (SharedPhysicsSystem.cs:224).

5. ONE SetTiles onto the new grid (SharedMapSystem.Grid.cs:839). One call = one TileChangedEvent = one CE connector re-flood (CEZGridConnectorSystem.cs:105).

6. MOVE ENTITIES, BEFORE emptying the source tiles (the GridFixtureSystem.cs:322-323 rule — otherwise DeparentAllEntsOnTile / your own empties race you). Query once with GetLocalEntitiesIntersecting(groundMap, new PhysShapeCircle(radius, centre), Transform.Empty, set, LookupFlags.Uncontained, lookup) (LocalQueries.cs:74) — grid-local so a hull parked over the circle is not scooped up, and Uncontained so container contents ride with their container. Then per entity: skip anything whose ParentUid is not the ground map; for anchored ones Unanchor (Component.cs:143, which strips the old snap cell) then AnchorEntity((uid, xform), (chunkGrid, chunkComp), sameTileIndices) (Component.cs:73 — the overload that does NOT demand a matching GridUid); for unanchored ones SetParent to the chunk grid (Component.cs:773). ReAnchor is internal and asserts same MapID (Component.cs:21, :54) so it is unavailable once the chunk leaves the ground map. Expect an AnchorStateChangedEvent pair per anchored entity, which re-dirties the CE connectors (CEZGridConnectorSystem.cs:68) and re-evaluates CE body activation (CESharedZLevelsSystem.Activation.cs:24) — all coalesced into the same tick.

7. TELL THE BIOME the props are gone: from a _WF partial of the sealed BiomeSystem (namespace Content.Server.Parallax; precedent CEZLevelsSystem.WFVirtualMass.cs), remove each moved uid from BiomeComponent.LoadedEntities and add its tile to ModifiedTiles. BiomeComponent is [Access(typeof(SharedBiomeSystem))] (BiomeComponent.cs:12), so this is the only legal route. Without it the entries leak until the chunk next unloads (BiomeSystem.ChunkLoader.cs:245) and OnEntityTerminating can no longer find them (BiomeSystem.cs:114-120).

8. STAMP THE HOLE with one more SetTiles on the ground map. Decide the tile first — this is the load-bearing choice:
   - Tile.Empty is the only value that makes anything fall. CE's ground test is literally `!tileRef.Tile.IsEmpty` (CESharedZLevelsSystem.Movement.cs:247, HasTileAbove :277). A cosmetic non-empty crack-hole tile is solid ground: mobs walk on it, the chunk lands on it, HasGroundUnderFootprint (Gravity.cs:629) reports support, and F7's chunk never reaches the ground layer.
   - Tile.Empty costs: decals on those tiles are refused (DecalSystem.cs:315) and existing ones wiped (DecalSystem.cs:175-195); fully-emptied 16x16 chunks are deleted outright (ClearEmptyMapChunks, SharedMapSystem.Grid.cs:702-711) so the ModifiedTiles pin from step 2 is the only thing keeping the hole; and DeparentAllEntsOnTile fires per empty tile but no-ops on a planet map (SharedTransformSystem.cs:116 vs Component.cs:775).
   RECOMMENDATION: make the hole Tile.Empty, and use a non-empty `WFFloorCrackRim` tile (or just the existing biome tile plus decals) for the one-tile rim ring, where crack_rim/crack_ring decals are legal. Do NOT model the hole as a chasm variant: chasm is an anchored StepTrigger entity whose ChasmSystem QueueDels the tripper after 1.8 s (ChasmSystem.cs:46, ChasmFallingComponent.cs:23) and _CE has zero chasm integration (the two `using Content.Shared.Chasm` lines in _CE are unused), so a chasm hole would delete players instead of dropping them a layer. If a walk-in-and-drop trigger is wanted later, write a _WF StepTrigger system that calls the CE descent, not ChasmSystem.

9. DECALS. Place the ring on the rim in the GROUND grid's local frame: TryAddDecal(protoId, new EntityCoordinates(groundMap, tileIndices + offset), out id, color, rotation, zIndex, cleanable:false) (DecalSystem.cs:296). Coordinates are raw grid-local Vector2 with the texture's bottom-left corner on the point (Decal.cs:11), so subtract half a tile if you want it centred. Rotation must come from the Angle argument — the placeholder RSIs' `directions: 4` is dead because DecalOverlay only draws Frame0 (DecalOverlay.cs:97). Store the returned uint ids on the cracker/chunk component for cleanup via RemoveDecal (DecalSystem.cs:331), or sweep with GetDecalsIntersecting (:356); design D19 keeps them for the round, so cleanup is only needed on admin teardown.

10. PUT THE CHUNK IN THE BERTH. Copy MoveGridSetToMap's body (Transit.cs:341-383): raise nothing CE-specific you do not need, capture world pose, `_transform.SetCoordinates(chunkGrid, xform, new EntityCoordinates(orbitMap, berthWorldPos), rotation: worldRot)`, restore velocities, then RaiseZMoveEventOnPassengers-equivalent so riders' CurrentZLevel and ground-height caches update (Transit.cs:389, CESharedZLevelsSystem.Movement.cs:153-159). This reparent is what finally fires EntParentChangedMessage -> CEZLevelsSystem.RefreshGridZPhysics (Transit.cs:62-65, :77) and grants CEZPhysicsComponent + CEZGridFallerComponent with its 3 s grace. Creating the grid directly on the orbit map would skip BOTH paths (GridAddEvent fires in nullspace, MapManager.GridCollection.cs:112 vs :121; the pre-init AttachParent produces no MoveEvent, Component.cs:630) and SweepMapGridsForZPhysics has no callers — the chunk would silently have no z-physics.

11. PARK IT. F0's exemption needs nothing on the chunk: WfIsOrbitLayer tests the MAP (Gravity.cs:93, CEZLevelsSystem.Wolfgate.cs:8), so any grid on the orbit map is skipped. Belt and braces: ForceAnchor makes the body Static, which Gravity.cs:96-97 also skips. But ForceAnchorComponent only acts on MapInitEvent (ForceAnchorSystem.cs:40) and a code-built grid is never map-initialised (MapManager.GridCollection.cs:127-128), so call `_shuttle.Disable(chunkGrid, force: true)` + EnsureComp<PreventGridAnchorChangesComponent> directly, and EnsureComp<ShuttleComponent> first or F7 can never release it (ShuttleSystem.cs:204 vs :218). Do not add MapGridComponent to the orbit MAP (WFPlanetNetworkSystem.cs:234-235).

12. CALL `_connectors.MarkDirty()` (CEZGridConnectorSystem.cs:58) after the cross-map move, since the connector system resolves links by world position but does not subscribe MoveEvent.

BATCHING RULE: the whole extraction should produce exactly three TileChangedEvents — ReserveTiles' generate, the chunk fill, the hole stamp — and they can be reduced to two by having the ReserveTiles pass and the read share one list. Each one costs a full CE connector re-flood plus a per-changed-tile broadphase query in CESharedZLevelsSystem.Movement.OnTileChanged (:122).

TESTS worth writing headless (per the design §9 list): tile count on the chunk equals the disc's tile count and both anchors moved; every disc tile on the ground map is in BiomeComponent.ModifiedTiles after extraction; drive one biome unload cycle and assert the hole survives; a mob standing inside the circle ends up parented to the chunk grid with its CEZPhysics CurrentZLevel updated; a mob standing on the rim keeps its ground; the chunk grid has CEZPhysicsComponent and CEZGridFallerComponent after the berth move; a pull between an inside and an outside entity is cleanly ended rather than left dangling.

### Risks

- ReserveTiles silently pins nothing for a tile whose biome layers produce no tile (BiomeSystem.PlanetSetup.cs:95-98 `continue` without touching `modified`). Any such tile in the disc is left unpinned and will be regenerated or re-emptied later. Verify coverage after the reserve pass instead of assuming it.
- ReserveTiles takes its bounds in GRID-LOCAL coordinates (GetLocalTilesIntersecting at BiomeSystem.PlanetSetup.cs:81) while every existing caller passes a world AABB. This only works because a biome planet layer sits at identity. If a planet layer ever gains an offset or rotation, both the existing callers and F5 silently reserve the wrong region.
- ReserveTiles calls SetTiles on the caller's list WITHOUT clearing it (BiomeSystem.PlanetSetup.cs:106). Reusing a list across calls re-applies every previous entry. WFPlanetNetworkSystem.cs:136 and ShuttleSystem.FasterThanLight.cs:1420 both Clear() first; F5 must too.
- BiomeComponent, LoadedEntities and ModifiedTiles are [Access(typeof(SharedBiomeSystem))] (BiomeComponent.cs:12). Any F5 bookkeeping must live in a partial of the sealed BiomeSystem or go through ReserveTiles. A new standalone system cannot touch them and will fail the access analyser, not at runtime.
- Every SetTiles wakes CESharedZLevelsSystem.OnTileChanged, which does ONE map-wide `_lookup.GetEntitiesIntersecting` per changed tile inside the handler (CESharedZLevelsSystem.Movement.cs:114-128). A radius-22 disc is ~1520 tiles, so ~1520 broadphase queries in a single frame, three times over. This is the real cost of the extraction, not the CE connector re-flood (which is coalesced to one pass per tick).
- CEZGridConnectorSystem.MarkDirty is set by ANY TileChangedEvent anywhere (CEZGridConnectorSystem.cs:105) and one re-flood walks every connector in the world doing two TryFindGridAt + TryGetTileRef probes each (:305-319, :244-290), plus an O(networks x members) survivor search per component (:203). F1F3 already flagged this as 'the path F5's extraction will hammer'.
- Emptying the disc can delete whole MapChunk objects on the ground map (ClearEmptyMapChunks, SharedMapSystem.Grid.cs:702-711 RemoveChunk) and, if the grid ever ran out of chunks entirely, raise EmptyGridEvent (:607-608). After chunk removal GetTileRef fabricates Tile.Empty again — the hole exists only in BiomeComponent.ModifiedTiles, so losing that pin silently restores terrain over the hole.
- Moving the chunk grid from the ground map to the orbit map runs SharedPhysicsSystem.HandleMapChange -> RecursiveMapUpdate -> ClearJoints on the grid AND every descendant (SharedPhysicsSystem.cs:184-212). Pull joints, dock WeldJoints and any tether joint on the chunk or on anything riding it are destroyed with no popup and no log. Anything docked to the chunk must be re-docked (RedockDocks, as MoveGridSetToMap does at Transit.cs:379) or it drifts.
- AnchorEntity returns false when the target tile's snap cell is already occupied (Component.cs:79-80) — the new grid starts empty so this is fine per tile, but a 3x3 anchor machine occupies only ONE snap cell (F1F3 A.2) while its fixture spans nine. If two moved entities claim the same index the second silently fails to anchor and ends up Dynamic on an orbiting grid.
- Design D6 sends players up with the chunk. Reparenting a player's mob across maps changes MapUid for the whole subtree (ChangeMapIdRecursive, Component.cs:673) including pause state (:667), and their z-physics caches are stale until a CEZLevelMapMoveEvent arrives (CESharedZLevelsSystem.Movement.cs:153-159, raised only by MoveGridSetToMap's RaiseZMoveEventOnPassengers at Transit.cs:381). Copying only the SetCoordinates half of MoveGridSetToMap leaves riders reading the ground layer's cached altitude.
- CEZLevelsSystem.RefreshGridZPhysics is private and reachable only via GridAddEvent (fires in nullspace for a code-built grid) or EntParentChangedMessage on MapGridComponent. Its only bulk fallback, SweepMapGridsForZPhysics (Transit.cs:67), has NO callers anywhere in Content. A chunk grid created directly on the orbit map therefore gets neither CEZPhysicsComponent nor CEZGridFallerComponent, and the failure is invisible until F7 tries to drop it (TryEnterTransit does EnsureComp<CEZPhysicsComponent> at Transit.cs:482 but nothing ensures the faller).
- ForceAnchorComponent is inert on a code-built grid: it acts only from MapInitEvent (ForceAnchorSystem.cs:40) and MapManager.CreateGrid deliberately skips map init (MapManager.GridCollection.cs:127-128). Adding the component and assuming the chunk is now static is a silent no-op — the same class of bug WFTestGridFactory.cs:43-45 documents for the berth marker.
- ShuttleSystem.Enable requires ShuttleComponent and returns silently without it (ShuttleSystem.cs:204) while Disable does not (:218). A chunk grid force-anchored without a ShuttleComponent can never be released, so F7's drop fails with no error. EnsureComp<ShuttleComponent> before force-anchoring, and read BodyType back after releasing.
- Nothing in the codebase pins the disc between ReserveTiles and extraction except ModifiedTiles, and the 10 s unload pass writes Tile.Empty back (BiomeSystem.ChunkLoader.cs:294) whenever no viewer is near — with the crew in orbit BiomeSystem.Update early-returns entirely (BiomeSystem.cs:198-202), so the ground layer can be wholly absent at the moment of extraction. Reserve immediately before reading, in the same tick, not at crack start.
- TryAddDecal refuses any coordinate whose tile IsSpace (DecalSystem.cs:315) and OnTileChanged deletes decals on tiles that become space (:175-195). Ordering matters: stamping the hole after placing ring decals destroys the ones that landed inside it. Place decals on the rim only, and place them after the stamp so the refusal is loud rather than a later silent deletion.
- Smimsh on placement (design F5) calls _biomes.ReserveTiles on the crush map for every hard fixture (ShuttleSystem.FasterThanLight.cs:1421) and breaks out of its fixture loop entirely when xform.MapID equals the ticker's DefaultMap (:1406). On the orbit layer the ReserveTiles call no-ops, but in a test fixture whose maps are the default map Smimsh does nothing at all — a test asserting 'placement crushed the obstruction' can pass or fail on which map the fixture built.
- GridFixtureSystem's split path is server-only and guards itself with `_isSplitting`. The new chunk grid, unlike the ground map, DOES get fixtures and split checks (RegenerateCollision's non-map branch, SharedMapSystem.Grid.cs:630+). A disc is contiguous so it yields one node, but a disc with an interior ring of empty tiles (a pre-existing lake or chasm on the surface) can split the chunk into multiple grids the moment it is filled, before anything has been parented to it.
- Design F5 says the chunk gets no atmosphere (D3). The chunk grid is a real grid on the orbit map whose atmosphere comes from the orbit map's own space mixture (WFPlanetNetworkSystem.cs:213 SetMapAtmosphere(orbit, true, GasMixture.SpaceGas)) — but the copied biome tiles are not isSpace tiles, so AtmosphereSystem's TileChangedEvent handler (AtmosphereSystem.cs:72) will treat them as sealed floor. Whether the chunk ends up airtight depends on whether a GridAtmosphereComponent is added, which nothing in the create path does.
- A radius-22 disc is ~1520 tiles at 0.5 mass each = ~760 grid mass (F1F3 already notes this against WFCentrifuge.maxHandledMass 3000). MassDataChangedEvent on the chunk grid also drives CEZGridSyncSystem.OnMassChanged (:158) — harmless while the chunk has no network, but it becomes live the moment anything gives the chunk a CEZGridComponent.

### Stale design claims

- PLANET_CRACKER_DESIGN.md §4 F5 'Biome gotchas': "The hole must be written through the biome's ModifiedTiles path (any tile set through the map API is recorded there)". FALSE. BiomeSystem subscribes no TileChangedEvent at all — the full subscriber list is AtmosphereSystem.cs:72, DecalSystem.cs:71, ExplosionSystem.cs:124, PathfindingSystem.Grid.cs:47, NavMapSystem.cs:56, ThrusterSystem.cs:60, RequiresTileSystem.cs:21, CEZGridConnectorSystem.cs:73, SharedSubFloorHideSystem.cs:36, CESharedZLevelsSystem.Movement.cs:24, CESharedZLevelsRoofSystem.cs:35, CEIconSmoothSystem.cs:33, SharedTransformSystem.cs:63. Tiles written with SharedMapSystem.SetTiles are NOT recorded in BiomeComponent.ModifiedTiles; the pin must be written explicitly, through ReserveTiles or a _WF partial of BiomeSystem.
- PLANET_CRACKER_DESIGN.md §4 F5: "extraction must call BiomeSystem.Preload on the circle's bounds before reading tiles, or unloaded chunks come back empty". Preload (BiomeSystem.PlanetSetup.cs:152) only inserts marker-layer chunk origins into the transient _markerChunks dictionary, which is cleared at the end of every update (BiomeSystem.cs:244). It generates no tiles, entities or decals and cannot make the disc readable. ReserveTiles (BiomeSystem.PlanetSetup.cs:76) is the call that generates and pins tiles.
- PLANET_CRACKER_DESIGN.md §4 F0 (pre-'As built' text): "The orbit layer gets CEZOrbitLayerComponent and UpdateGridGravity skips grids parked there the same way it skips the ground layer." As built the component is WFOrbitLayerComponent (Content.Shared/_WF/PlanetCracker/Planets/WFOrbitLayerComponent.cs:9) reached through WfIsOrbitLayer (CEZLevelsSystem.Wolfgate.cs:8) at Gravity.cs:93, and there is no ground-layer skip to be 'the same way' as — the ground case falls out of RigidSetHasSupport (Gravity.cs:102) / HasGroundUnderFootprint (:629) reading live tiles. The F0 'As built' note supersedes this correctly; the earlier paragraph is stale.
- PLANET_CRACKER_DESIGN.md §4 F5: "stamp the hole (tiles inside the circle become the crack-hole tile, the rim gets a decal ring)". These two clauses cannot both hold with a single tile. A non-empty crack-hole tile is solid ground to CE (CESharedZLevelsSystem.Movement.cs:247), so nothing falls into it and F7's chunk lands on it; a Tile.Empty hole makes TryAddDecal refuse (DecalSystem.cs:315) and DecalSystem.OnTileChanged wipe (:175-195) anything already there. The rim ring must sit on non-empty rim tiles outside the hole.
- ASSET/design implication of the placeholder sprites: crack_ring.rsi and crack_rim.rsi declare `directions: 4` per state, but DecalOverlay only ever draws Frame0 of the state (Content.Client/Decals/Overlays/DecalOverlay.cs:97) and takes orientation from the decal's own Angle (:110-114). The four directions are dead art; either the sprites should be single-direction or the plan should stop treating decal orientation as sprite-driven.
- F1F3_IMPLEMENTATION_PLAN.md OPEN RISKS: "UnloadTiles writes Tile.Empty back roughly 10 s after the last viewer leaves (BiomeSystem.ChunkLoader.cs:294)". Accurate per chunk but misleading in aggregate: UnloadChunks returns after the FIRST chunk it unloads (BiomeSystem.ChunkLoader.cs:321) and only runs on the 10 s UnloadInterval (BiomeSystem.cs:60), so the real rate is one 8x8 chunk per 10 s per biome. Also, BiomeSystem.Update early-returns before any load or unload when no tracked viewer exists at all (BiomeSystem.cs:198-202), so with everyone in orbit the ground layer neither loads nor unloads — the risk is 'the disc was never generated', not 'the disc is being emptied'.
- F1F3_IMPLEMENTATION_PLAN.md OPEN RISKS: "An anchored machine over an emptied tile does NOT fall or unanchor on a planet map. DeparentAllEntsOnTile reparents survivors to gridXform.MapUid (SharedTransformSystem.cs:116), and on a biome map the grid IS the map, so SetParent hits its own early-out (SharedTransformSystem.Component.cs:776-777)." Confirmed, and stronger than stated: DeparentAllEntsOnTile never calls Unanchor at all, so even on an ordinary grid it reparents without clearing xform._anchored or the snap-grid cell — the 'de-parents and unanchors' in its own doc comment (SharedTransformSystem.cs:84) is wrong. F5 cannot rely on any part of this path.
- F4_IMPLEMENTATION_PLAN.md section 3 step 1 contains an in-line self-correction that was never resolved: "...stays Static for the whole fall (ShuttleSystem.cs:207-208 — wait, the un-forced guard is :205-206)". Verified: the PreventGridAnchorChangesComponent guard in Enable is at Content.Server/Shuttles/Systems/ShuttleSystem.cs:207-208 and in Disable at :221-222; the required-ShuttleComponent Resolve is at :204. The parenthetical should be deleted and the cite fixed to :207-208 before F5 copies it.

## Beams across z-layers and the crack ring

### Summary

HOW THE Z-PASSES WORK (verified)

ScalingViewport.RenderZLevels (Content.Client/_CE/ZLevels/Core/ScalingViewport.CEZLevels.cs:99) builds a list of (MapUid, Depth, AllowFov, Transit) passes (:94, :128), sorts them painter-style (:268-275) and calls viewport.Render() once per pass (:405) with viewport.ClearColor = Black only on the first (:403). Every pass therefore re-runs EVERY registered overlay, with OverlayDrawArgs.MapId/MapUid taken from vp.Eye.Position.MapId (RobustToolbox/Robust.Client/Graphics/Clyde/Clyde.HLR.cs:145-146). That is exactly why WFCrackCircleOverlay.cs:83-84 filters on args.MapId and why one filter is the whole layer gate.

Per-pass eye (ScalingViewport.CEZLevels.cs:337-353):
  Position = MapCoordinates(_fallbackEye.Position.Position, passMap)   (:344) — the SAME world XY in every pass
  Rotation = _fallbackEye.Rotation                                     (:351) — identical in every pass
  Offset   = _fallbackEye.Offset + (-_fallbackEye.Rotation).ToWorldVec() * ZLevelOffset(0.7) * (depth - ownDepth)   (:337-339)
  Scale    = _fallbackEye.Scale * pow(ZLevelViewShrink(0.85), -depth)  (:340, :352)
ownDepth = -GetLocalAltitude(player) (:147-148). Eye.Scale is a multiplier on apparent size (RobustToolbox/Robust.Shared/Graphics/Eye.cs:65-73), so a lower pass is drawn SMALLER and, with eye rotation 0, 0.7 world units LOWER per level.

WHAT AN OVERLAY CAN KNOW IN A LOWER PASS
- The pass's map: args.MapId / args.MapUid.
- The pass's eye Offset / Scale / Rotation / Position: args.Viewport.Eye (a plain IEye read; no cast needed).
- The pass depth: ((ScalingViewport.ZEye)args.Viewport.Eye).Depth (:632), plus LowestDepth/HighestDepth (:631/:633) and Primary (:646). CEZLevelBlurOverlay.cs:35-44 and :63-64 are the precedent.
- TRAP: in the viewer's own pass with the player grounded, viewport.Eye is set to _fallbackEye verbatim (:328-331), which is NOT a ZEye. So `is ZEye` is false and ZEye.Primary is unreachable exactly in the pass you most want to identify. Primary is only ever set in the else-branch (:346), i.e. when the player is airborne. Identify the own pass by args.MapId == player's TransformComponent.MapID instead.
- The viewer's own map: IPlayerManager.LocalEntity -> TransformComponent.MapUid (the same route RenderZLevels itself takes at :114-126).

THE ONLY PROJECTION YOU NEED (derived from :339/:340/:344/:351/:352)
All z-maps share one world coordinate space (CEZGridConnectorOverlay.cs:17-24), so an anchor at world XY A on the ground has the numerically identical XY on the orbit map. But A drawn in the orbit pass lands NOWHERE NEAR where the ground pass drew the anchor. To get the point X, in the CURRENT pass's world coordinates, that renders on top of a target at world XY A on another layer:

  n  = CEZMapComponent.Depth(args.MapUid) - CEZMapComponent.Depth(targetMap)      // integer level difference
  up = (-args.Viewport.Eye.Rotation).ToWorldVec()                                  // (0,-1) at rotation 0
  r  = MathF.Pow(CESharedZLevelsSystem.ZLevelViewShrink, n)                        // 0.85^n
  E  = args.Viewport.Eye.Position.Position ; O = args.Viewport.Eye.Offset
  X  = E + O + r * (A - E - O + up * CESharedZLevelsSystem.ZLevelOffset * n)

The player's altitude terms cancel exactly, so n is a pure map-depth difference and no GetLocalAltitude/GetAbsoluteAltitude call is needed. The inverse direction (ground pass looking at an orbit target) is the same formula with n negative (r = 0.85^-4 = 1.916).

CONCRETE ANSWER FOR PROJECTOR(ORBIT) -> ANCHOR(GROUND)
Stack today: ground 0, air 1, air 2, cloud 3, orbit 4 (Resources/Prototypes/_WF/PlanetCracker/planets.yml:7-8), so n = 4 either before or after F4's cloud change.

ORBIT PASS (the viewer's own pass, and the only pass that should draw the long beam):
  near end = the projector's real world position P on the orbit map (_transform.GetWorldPosition).
  far  end = X with n = 4, r = 0.85^4 = 0.522, up*0.7*4 = (0,-2.8) at eye rotation 0:
             X = E + O + 0.522*(A - E - O) + (0, -1.462)
  So: NOT "the anchor's world XY at the ground pass's shrink" as the design sketch puts it — the shrink is about the EYE CENTRE, and there is an additional fixed 1.462-world-unit downward perspective drop. Feeding A in raw misses the drawn anchor by (1-r)*|A-E| + 1.46 tiles, i.e. ~8-12 tiles at the screen edge on a 22-tile cut. Both corrections are required.
  The own pass is rendered AFTER every below pass (:268-275 sorts depth ascending, own map appended at :208 after the walk), and ClearColor is null for non-first passes (:403), so anything drawn in the own pass at OverlaySpace.WorldSpace composites on top of the already-painted ground layer, after lighting and after FOV (Clyde.HLR.cs:544, :570-575, :603-609). No unshaded shader is needed: WorldSpace is already post-lighting.

GROUND PASS: do not draw the long beam here at all. The projector is 4 levels up and is NEVER rendered from the ground — look-up adds exactly ONE map above (:215-218), i.e. air layer 1. Drawing toward X with n = -4 puts the far end 1.9x magnified and 2.8 units up, far off-screen, over a pass that is appended last in the sort (aUp branch, :270-273) and would paint over it anyway.

WHAT THE VIEWER ON THE GROUND SEES LOOKING UP: air layer 1 only (empty sky), never the orbit hull or the projector. The beam must be a local object: a server-spawned 32x160 sky_beam sprite entity standing at each anchor, unconditionally (not gated on look-up). That same entity is also what the orbit viewer sees inside the ground pass — shrunk 0.522x and blurred/tinted by CEZLevelBlurOverlay (CEZLevelBlurOverlay.cs:38 applies only at Depth &lt; 0) — so the overlay beam from the projector and the sky-beam stub read as one continuous column.

### Risks

- The far-end projection is NOT just 'the anchor's world XY at the ground pass's shrink', as the design sketch in PLANET_CRACKER_DESIGN.md:212 puts it. The shrink is about the EYE CENTRE (ScalingViewport.CEZLevels.cs:344 keeps the same eye world XY in every pass, :352 scales), and there is a SECOND, additive perspective term: up * 0.7 * n (:339). Feeding the raw anchor XY into an orbit-pass beam misses the drawn anchor by (1-0.85^4)*|A-E| + 1.46 world units — about 8-12 tiles when the anchor is near the screen edge. Both terms are mandatory.
- args.Viewport.Eye is NOT a ZEye in the viewer's own pass while the player is grounded (ScalingViewport.CEZLevels.cs:328-331 assigns _fallbackEye verbatim). Any `is ZEye` / ZEye.Primary test as a 'this is my own layer' gate silently never fires for a player standing still — the most common case. ZEye.Primary is only ever set in the else branch (:346), i.e. when the player is airborne.
- Today's committed planets.yml still has airLayers: 2 and cloudLayer: true (:7-8), so the orbit->ground walk breaks at the cloud (ScalingViewport.CEZLevels.cs:186-191) AND the cloud's own pass paints an opaque full-screen deck (:377). Until F4 lands the flip, an orbit viewer renders depth 3 only: no ground pass, no ground anchors, no crack ring, and the far end of any beam has nothing under it. The beam overlay is untestable from orbit before that YAML change.
- Two WorldSpace overlays in the same pass with equal ZIndex draw in RANDOM order (Overlay.cs:33-35). CEZLevelBlurOverlay is WorldSpace with no ZIndex (CEZLevelBlurOverlay.cs:23). Any beam geometry drawn inside a LOWER pass would be blurred or not at random between frames. Drawing only in the own pass sidesteps this entirely; if a lower-pass beam is ever wanted, it needs an explicit ZIndex.
- Overlay exceptions are swallowed into the 'clyde.overlay' sawmill and never crash (Clyde.HLR.cs:160-168). A wrong transform, a null eye, or a missing CEZMapComponent presents as 'the beam is just not there'. Every early-out should be a guard with a distinguishable log, and verification needs a running client.
- Anything drawn in the own pass is painted over by the above passes, which the sort puts last (ScalingViewport.CEZLevels.cs:270-273) — including the look-up pass (:215-218) and every transit map above the observer (:212-213, RenderTransitOverhead :357). With look-up toggled on, a beam drawn in the own pass will sit under whatever the layer above renders.
- RSI frames are AtlasTexture sub-regions of one packed sheet (RSIResource.cs:225). UV.y > 1 to tile a beam texture samples the NEXT ANIMATION FRAME on the sheet, not a repeat. Tiling must be one quad per repeat.
- The 32x32 crack_beam frame stretched over a 20-44 tile beam is a ~40x vertical smear. With the placeholder gradient this reads acceptably; with any future art that has structure along its length it will not, and the switch to per-tile quads or a tapering triangle list is a rewrite of the draw call, not a tweak.
- A constant-width Box2Rotated beam does not taper, so it visually contradicts the 0.522x shrink at the far end: the beam looks the same thickness where it meets a half-size anchor. Acceptable for a glow; noticeable if the texture gains hard edges.
- SpriteComponent.Offset on the sky beam is reset every render frame to zPhys.SpriteOffsetDefault for any entity carrying CEZPhysicsComponent (CEClientZLevelsSystem.cs:86-90). If the beam entity ever acquires CEZPhysics (e.g. it ends up on a grid pushed into transit, CEZLevelsSystem.Transit.cs:91/:482), a runtime-set offset is clobbered and only the YAML value survives. Set the offset in YAML.
- The projector's 64x64 art already overhangs its 1x1 fixture (F1F3 OPEN RISKS, machines.yml:99-102). The beam's near endpoint at GetWorldPosition(projector) is the machine's tile centre, not the visible emitter, so the beam will appear to start inside the sprite. A hand-tuned emitter offset rotated by the projector's world rotation is needed, and it must track Rotatable (machines.yml:132-133).
- MaxZLevelsBelowRendering is a hard-coded static 10 (CESharedZLevelsSystem.Constants.cs:10). The CVar ce.zlevels.rendering.max_zLevels_below_rendering (CCvars.CEZLevels.cs:51, default 1, SERVER|REPLICATED) is declared and NEVER READ anywhere in the tree. Nothing can be tuned through it, and a future wiring of that CVar to its default of 1 would cut the orbit->ground walk to one layer and silently break the beam's far end.
- Look-up is refused and auto-cancelled under any opaque tile above the player (CESharedZLevelsSystem.View.cs:25-35, :44-48, HasOpaqueAbove :54-73). A player standing inside a roofed structure on the surface cannot look up at all, so any design that relies on look-up for the ground-side beam fails indoors as well as by distance.
- Decals draw Frame0 only (DecalOverlay.cs:97 -> SpriteSystem.Helpers.cs:25-28 -> IRsiStateLike.Default). crack_ring and crack_rim are authored with directions: 4 (128x32 sheets), so three quarters of every ring png is unreachable through the decal path. Either fix the metas to directions: 1 or those states must be driven through a sprite entity instead.
- Each pass runs every overlay, so a beam drawn per pass multiplies by the number of passes — 5 from orbit once the cloud is dropped (air-3, air-2, air-1, ground, own; F4_IMPLEMENTATION_PLAN.md:280 already corrects this to FOUR below passes plus the player's own). The existing circle overlay already spends ~176 line segments per pass at a 22-tile radius (F1F3 OPEN RISKS). Anything new that is not single-pass compounds that.

### Stale design claims

- PLANET_CRACKER_DESIGN.md:212 (D4): 'from the projector's screen position to the anchor's position projected onto the layer below, using the same transform the z-level renderer already uses'. The renderer does not expose a transform to reuse — there is no helper. The overlay must re-derive the projection from ScalingViewport.CEZLevels.cs:339 (offset = up*0.7*(depth-ownDepth)) and :340/:352 (scale = 0.85^-depth) by hand. Also, 'projected onto the layer below' understates it: the ground is FOUR layers below orbit, not one, and the projection has two terms (a shrink about the eye centre and a 0.7-per-level drop), not one.
- PLANET_CRACKER_DESIGN.md:212: 'On the surface, looking up, the same overlay draws the beam from the anchor to the projector's projected position above.' Not achievable. Look-up renders exactly one map above (ScalingViewport.CEZLevels.cs:215-218) and the projector is four levels up, so the orbit layer is never a pass from the ground. The projected far end lands ~1.9x magnified and off-screen over content that does not exist, and the above pass is sorted last (:270-273) and would paint over it. Only the sky_beam sprite entity works on the surface.
- PLANET_CRACKER_DESIGN.md:212: 'without look-up, a tall sky-beam sprite stands at each anchor' — implying the sprite is the look-up fallback. Since look-up can never reach orbit, the sky beam is not a fallback, it is the ONLY surface-side beam, and it should be spawned unconditionally. It is also the orbit viewer's near-anchor half of the beam (it renders in the ground pass), which the design does not mention.
- PLANET_CRACKER_DESIGN.md:212: 'Animated beam texture, additive shader.' No additive shader is needed if the beam is drawn at OverlaySpace.WorldSpace, which runs after lighting AND after FOV (Clyde.HLR.cs:570-575, :603-609). The 'unshaded' shader the upstream BeamVisualizerEvent defaults to (SharedBeamComponent.cs:104) is a SPRITE-layer concept and does not apply to an overlay at all.
- PLANET_CRACKER_DESIGN.md:28 and F1F3 A-table treat Content.Server/Beam/BeamSystem.cs as merely 'same map only'. It is worse than that for this use: CreateBeam spawns ONE ENTITY PER TILE of length (:121-128) with a network event per segment (:103-104, :126-127) and an EdgeShape fixture per beam (:81-99). A 44-tile cut would be ~44 entities per beam. The rejection is right; the stated reason undersells it.
- PLANET_CRACKER_DESIGN.md:31 lists CEZLevelBlurOverlay under 'Looking up and down through layers' as if it participates in look-up. It does not: CEZLevelBlurOverlay.cs:38 returns false for any pass with Depth >= 0, so it only ever touches layers BELOW the observer. Nothing blurs or tints the look-up pass.
- F1F3_IMPLEMENTATION_PLAN.md OPEN RISKS (:1369) says the crack circle is invisible from orbit and lists three options for F4/F5. F4_IMPLEMENTATION_PLAN.md:283 already took option one (drop the cloud layer, airLayers 2->3), so the risk is resolved in the plan — but NOT in the tree: Resources/Prototypes/_WF/PlanetCracker/planets.yml:7-8 still reads airLayers: 2 / cloudLayer: true. Anyone reading the F1F3 risk as current, or the F4 decision as landed, will be wrong in opposite directions.
- F1F3_IMPLEMENTATION_PLAN.md D.1 (:622) documents the ring call as `handle.DrawPrimitives(LineStrip, ring.Span, Color.ToSrgb(colour))` and :628 asserts 'DrawPrimitives does not do the sRGB conversion DrawCircle does — call Color.ToSrgb yourself'. That is backwards and the shipped code corrects it: the Vector2-span overload calls Color.FromSrgb internally (DrawingHandleBase.cs:117-124), so it takes the RAW skin colour, while DrawLine and unfilled DrawCircle need the caller-converted linear colour (WFCrackCircleOverlay.cs:110-122). - F1F3_IMPLEMENTATION_PLAN.md:632 says the circle overlay is 'visible there and from one or two air layers up'. The bound is not one or two: the downward walk runs to MaxZLevelsBelowRendering = 10 (ScalingViewport.CEZLevels.cs:182, Constants.cs:10) and only stops at a cloud or ground layer or an opaque floor. With the cloud gone the overlay is visible from every air layer and from orbit.

## The chunk in orbit and its drop

### Summary

API map for the chunk grid's life in orbit and its drop, read out of engine + _CE + upstream + committed F0/F1/F3 code in the worktree.

CREATION AND BERTH PLACEMENT. `IMapManager.CreateGridEntity(EntityUid map)` then `SharedTransformSystem.SetLocalPosition` is the in-repo precedent (Content.Server/_WF/PlanetCracker/Testing/WFTestGridFactory.cs:104-121); for a grid, parent == map so local == world. `SetWorldPosition` also works and is grid-safe: SetWorldPositionRotationInternal's re-parent branch is gated on `component.GridUid != uid`, which is false for a grid, so it always takes the map branch (RobustToolbox/Robust.Shared/GameObjects/Systems/SharedTransformSystem.Component.cs:1236-1247). Grid bookkeeping is automatic: OnGridMove / OnParentChange move the GridTree proxy and enrol the grid in `_physics.MovedGrids` (SharedMapSystem.Grid.cs:172-235). Two things fire the instant the grid initialises and both fight the design: ShuttleSystem.OnGridInit `EnsureComp<ShuttleComponent>` (+ ImplicitRoofComponent) at Content.Server/Shuttles/Systems/ShuttleSystem.cs:130-142, and ShuttleComponent.Enabled defaults true (Content.Server/Shuttles/Components/ShuttleComponent.cs:9) so OnShuttleStartup calls Enable -> BodyType.Dynamic, BodyStatus.InAir, FixedRotation false (:144-162, :201-213). A newly-cut chunk is therefore a free-floating dynamic shuttle until it is anchored. `ShuttleSystem.Smimsh(EntityUid uid, FixturesComponent? = null, MapGridComponent? = null, TransformComponent? = null, EntityUid? crushMap = null, bool explodeGrids = false, HashSet<EntityUid>? ignoredGrids = null)` is public at Content.Server/Shuttles/Systems/ShuttleSystem.FasterThanLight.cs:1384; per hard fixture it enlarges the AABB by 0.2, calls `_biomes.ReserveTiles`, gibs mobs and QueueDels other uncontained entities not on `uid` or in `ignoredGrids`, optionally CrushGrid-explodes intersecting grids (`includeMap: false`, so a biome map-grid is spared), and raises ShuttleFlattenEvent (:1396-1483). FTLAntiCollisionSystem is the only "find a clear spot" precedent (Content.Server/Shuttles/Systems/FTLAntiCollisionSystem.cs:64-242) and it runs only on FTLCompletedEvent, uses `_mapManager.FindGridsIntersecting` boxes, and does NOT re-dock docked grids after moving (:147) — the bug the F4 plan's snap step 7 avoids.

STATIC / TETHERED. `AddComp<ForceAnchorComponent>` at runtime does work: EntityManager re-raises MapInitEvent on an already map-initialised entity (RobustToolbox/Robust.Shared/GameObjects/EntityManager.Components.cs:428-429), so ForceAnchorSystem.OnForceAnchorMapInit runs `_shuttle.Disable(force: true)` + `EnsureComp<PreventGridAnchorChangesComponent>` (Content.Server/_NF/Shuttles/Systems/ForceAnchorSystem.cs:40-44). There is no release path in that 51-line file. PreventGridAnchorChangesComponent vetoes Toggle/Enable/Disable unless `force: true` (ShuttleSystem.cs:186-187, :207-208, :221-222). Enable requires ShuttleComponent as a Resolve dependency (:204) while Disable does not (:218) — for the chunk this is saved by OnGridInit's EnsureComp, unlike a hand-built hull.

CE NETWORK. Two static grids side by side on the orbit layer never form one CE grid network: CEZGridConnectorSystem.TryGetConnectorLinkDir only resolves a neighbour on the map ABOVE or BELOW (or the linked transit map) and rejects `neighbourGridUid == parentGrid` (Content.Server/_CE/ZLevels/Core/CEZGridConnectorSystem.cs:244-291); ComputeDesiredComponents builds edges only from those links (:305-319). No network means no CEZGridComponent, so CEZGridSyncSystem's OnGridMoved / OnGridBodyTypeChanged / OnMassChanged / PinStaticNetwork / IsStaticAnchor never touch either grid (CEZGridSyncSystem.cs:51-56, :119-156, :170-177, :469-495). What DOES attach is RefreshGridZPhysics: any grid on a CEZMapComponent or transit map gets `EnsureComp<CEZPhysicsComponent>` plus a fresh `CEZGridFallerComponent` with a 3 s grace (CEZLevelsSystem.Transit.cs:77-98, CEZGridFallerComponent.cs:44). On the orbit layer the fall sweep skips it twice — `WfIsOrbitLayer` (CEZLevelsSystem.Gravity.cs:93-94 -> Content.Server/_WF/PlanetCracker/Planets/CEZLevelsSystem.Wolfgate.cs:8) and BodyType.Static (:96-97).

GRAVITY. SharedGravitySystem.OnGridInit EnsureComps GravityComponent on every new grid with Enabled=false, Inherent=false (Content.Shared/Gravity/SharedGravitySystem.cs:202-205); GravitySystem.RefreshGravity then leaves it false because there is no gravgen parented to the chunk (Content.Server/Gravity/GravitySystem.cs:19-50). Weightlessness is `GridUid` gravity OR `MapUid` gravity (SharedGravitySystem.cs:161-172), and the orbit map carries no GravityComponent — `orbitComponents: []` in Resources/Prototypes/_WF/PlanetCracker/planets.yml:40, and only the air/cloud layers get `Gravity {enabled, inherent}` (:27-39). So crew on the chunk in orbit ARE weightless unless F5 writes gravity onto the chunk grid itself. The ready-made recipe is CEAutoGridGravitySystem.EnableGravity — `EnsureComp<GravityComponent>`, `Inherent = true`, `Enabled = true`, Dirty (Content.Server/_CE/ZLevels/Gravity/CEAutoGridGravitySystem.cs:46-52); Inherent is what stops RefreshGravity wiping it (GravitySystem.cs:24-25). CEAutoGridGravityComponent is referenced by no prototype in the repo, so putting it on the orbit map would newly give every arriving hull inherent gravity — prefer the per-grid write.

ATMOSPHERE. A grid with no GridAtmosphereComponent falls through to the map mixture: GetTileMixture resolves the grid first, then MapAtmosphereComponent, then GasMixture.SpaceGas (Content.Server/Atmos/EntitySystems/AtmosphereSystem.API.cs:161-186). The orbit map is space (`_atmos.SetMapAtmosphere(orbit, true, GasMixture.SpaceGas)`, Content.Server/_WF/PlanetCracker/Planets/WFPlanetNetworkSystem.cs:213), so D3 holds by default. BUT copying ~1500 tiles will hand the chunk an atmosphere anyway: AutomaticAtmosSystem subscribes MassDataChangedEvent on MapGridComponent and `AddComp<GridAtmosphereComponent>` as soon as `NewMass / ShuttleSystem.TileDensityMultiplier >= 7.0f` (Content.Server/Atmos/EntitySystems/AutomaticAtmosSystem.cs:22-32; TileDensityMultiplier = 0.5f, ShuttleSystem.cs:85) — i.e. at 7 tiles. There is no opt-out component; F5 must RemComp after the SetTiles batch or the chunk gets a 1500-tile simulated atmosphere.

LIGHTING. WFPlanetNetworkSystem does `RemComp<MapLightComponent>(orbit)` (:214) and absent MapLightComponent means `MapLightComponent.DefaultColor` = sRGB black ambient (RobustToolbox/Robust.Client/Graphics/Clyde/Clyde.LightRendering.cs:682-683, MapLightComponent.cs:15). On top of that the chunk keeps ImplicitRoofComponent (ShuttleSystem.cs:141), whose Color defaults to Black (Content.Shared/Light/Components/ImplicitRoofComponent.cs:11-12) — CE only strips it from grids that are in a z-grid network (CEZLevelsRoofSystem.Grids.cs:37-48), which the chunk is not. So the chunk in orbit is pitch dark except for PointLight entities riding it, and it also casts a roof shadow over itself.

WATCHDOG. Precedents: WFGravityAnchorComponent stores its owner as a `NetEntity? Cracker` (Content.Shared/_WF/PlanetCracker/Anchors/WFGravityAnchorComponent.cs:20-22) and WFGravityAnchorSystem runs a `_nextSweep`-gated 1 Hz EntityQueryEnumerator sweep (Content.Server/_WF/PlanetCracker/Anchors/WFGravityAnchorSystem.cs:276-298). CE's own orphan watchdog is CleanupOrphanedTransitMaps — `TerminatingOrDeleted` + `IsQueuedForDeletion` + "is the primary still on my map" then QueueDel (CEZLevelsSystem.Transit.cs:616-634), called from Update (CEZLevelsSystem.cs:143). For "off the map" use `HasComp<WFOrbitLayerComponent>(Transform(cracker).MapUid)`, the same test F4's Idle->Surveying edge uses.

THE DROP. F4's Fall order (Docs/PlanetCracker/F4_IMPLEMENTATION_PLAN.md:119-126): ReleaseLock (RemComp ForceAnchor + PreventGridAnchorChanges, `_shuttle.Enable(force: true)`, read back BodyType) -> set every centrifuge gravgen GravityActive false (Gravity.cs:65 skips inactive gravgens when pooling capacity) -> `EnsureComp<CEZGridFallerComponent>` with Velocity 0 and GravityTime = now -> `TryEnterTransit(grid, startProgress: 1.0f)` -> SetState(Falling). For a chunk with NO gravgen at all the automatic path also works: RigidSetHasSupport is false once the chunk is neither gravgen-lifted nor over ground (Gravity.cs:534-565) and the sweep calls TryEnterTransit for it — BUT only if it is not Static (:96-97) and not on an orbit layer (:93-94), which is exactly the chunk's situation, so on the orbit layer the sweep will NEVER drop it. F7 must call TryEnterTransit explicitly. TryEnterTransit is public at Transit.cs:407, returns false with no log when the map is already transit or lacks CEZMapComponent (:414-418), calls `_shuttle.Enable(gridUid)` un-forced per grid (:490) — so PreventGridAnchorChanges must be gone first — and adds a global PVS override (:486). Descent is driven by IntegrateFallingGrid -> SetTransitAltitude (Gravity.cs:267-401, Transit.cs:502-611) with GridGravity 0.15 levels/s², terminal 1.2, crash above 0.35 (CEZGridFallerComponent.cs:50-62).

CRASH SIZING. CrashGrid queues one explosion per hull tile at CrashTileIntensity 12 / slope 2 / maxTile 4, then one centre blast of `CrashIntensityPerTile (5) * tileCount` with CrashCenterSlope 5 and CrashCenterMaxIntensity 100 (Gravity.cs:406-431, CEZGridFallerComponent.cs:64-86). For ~1500 tiles the centre blast is 7500 total intensity capped at 100 per tile. It will NOT hang the server, for two reasons. First, QueueExplosion folds same-type explosions within `ExplosionPrototype.MaxCombineDistance` (default 1f, Content.Shared/Explosion/ExplosionPrototype.cs:87-91) into the first queued entry by summing TotalIntensity (Content.Server/Explosion/EntitySystems/ExplosionSystem.cs:386-400), so orthogonally adjacent tiles merge and only a ~1.4-spaced lattice of entries survives. Second, processing is hard-bounded per tick by ExplosionTilesPerTick (100) and ExplosionMaxProcessingTime (7 ms), with `SingleTickAreaLimit` 400 deferring big ones (ExplosionSystem.Processing.cs:84-159; CCVars.Explosion.cs:14-15, :67-68, :99-100). The real cost is the synchronous O(tiles x queued) combine scan inside CrashGrid's own loop — ~1500 x ~750/2 TryDistance calls in one tick — plus a couple of seconds of degraded TPS while the queue drains. MaxArea is 196608 and MaxIterations 500 (CCVars.Explosion.cs:46-57), both far above what 7500 intensity reaches.

DELETING THE GRID. RecursiveFlagEntityTermination + RecursiveDeleteEntity walk `xform._children`, so QueueDel on the grid deletes everything parented to it (RobustToolbox/Robust.Shared/GameObjects/EntityManager.cs:597-657). A player aboard is handled by MindSystem.OnMindContainerTerminating: transfer to a visiting entity if any, else TransferTo(null) and SpawnGhost at the dying entity's position when GhostOnShutdown (Content.Server/Mind/MindSystem.cs:53-83). CRITICAL ORDERING BUG WAITING TO HAPPEN: every explosion CrashGrid queues is an EntityCoordinates parented to the chunk grid (`_map.GridTileToLocal`, Gravity.cs:413; the centre blast resolves through TryGetMapOrGridCoordinates, SharedTransformSystem.Component.cs:1473-1502, which also lands on a grid), and SpawnExplosion returns null when `TerminatingOrDeleted(entPos.EntityId)` (ExplosionSystem.cs:427-428). QueueDel-ing the chunk in the same tick as the crash silently cancels the whole crash.

TRANSIT COLLISIONS. CheckTransitCollisions only enumerates CEZTransitMapComponent maps (Gravity.cs:151-221), so a cracker still parked static on the orbit layer is not in the scan at all — a lone falling chunk has one entry and the inner loop never runs. When both fall, the order-swap guard `prevDelta * curDelta > 0f -> continue` (:193-194) treats equal progress as a swap, hence F4's D-K staggering (1.0f vs 0.98f). Cross-plane Smimsh during TryHopConvoyGap passes NO ignoredGrids (Transit.cs:744) but the crossed planes are the bare air maps, which hold no grids; the landing Smimsh does pass `ignoredGrids: movedGrids` (:810) and so spares the falling set while still flattening whatever is on the ground under the footprint.

GROUND AND THE HOLE. HasGroundUnderFootprint takes the chunk's full world AABB (`GetWorldMatrix(grid).TransformBox(grid.Comp.LocalAABB)`) and returns true if ANY tile of the target map-grid in that box is non-empty (Gravity.cs:629-643). A 44-tile circular chunk's AABB is a 44x44 square whose corners sit on intact surface outside the cut, so the plane always reads "blocked" — the chunk stops at the ground layer's plane (progress 0, LandTransitSet -> TryExitTransit, Transit.cs:659-674) and lands ON the surface over the hole, never inside it. It could not do otherwise: the ground is depth 0, TryMapDown fails, and SetTransitAltitude's `progress < 0` branch falls straight to LandTransitSet (:564-586). The crash gate then re-tests HasGroundUnderFootprint on the landed map (Gravity.cs:382-385), which is true for the same reason, so CrashGrid fires. The design's crack-hole is a real tile anyway (Resources/Textures/_WF/PlanetCracker/Tiles/crack_hole.rsi/meta.json, single state `crack_hole`), so tile emptiness never enters it — and if it were left empty, Smimsh's own `_biomes.ReserveTiles` (FasterThanLight.cs:1421) plus BiomeSystem.OnShuttleFlatten (BiomeSystem.cs:141-172) would refill it with biome tiles on landing unless those indices are already in BiomeComponent.ModifiedTiles.

### Recommendations

1. CHUNK CREATION ORDER. `CreateGridEntity(orbitMap)` -> set position -> ONE batched `SetTiles` for the whole circle -> then, in this order: `RemComp<GridAtmosphereComponent>` (AutomaticAtmosSystem will have added it on the mass change), `EnsureComp<GravityComponent>{Inherent = true, Enabled = true}`, `EnsureComp<CleanupImmuneComponent>`, `AddComp<ForceAnchorComponent>`. Do not rely on tile-copy order; the mass change fires inside SetTiles, so the atmos RemComp must come after.

2. BERTH PLACEMENT. Use `SharedTransformSystem.SetWorldPosition` (grid-safe, SharedTransformSystem.Component.cs:1236) with the berth rect from F4's `TryGetBerthRect`, which is the single derivation. Run FTL-anti-collision-style clearance yourself with `_mapManager.FindGridsIntersecting(orbitMapId, berthBox, approx: false, includeMap: false)` and refuse rather than search — the orbit layer has no terrain to search around and the design guarantees the berth is clear. Then `Smimsh(chunk, explodeGrids: true, ignoredGrids: {cracker and its docked set})` — note that without `ignoredGrids` a berth that overlaps the cracker's own AABB by 0.2 tiles of fixture enlargement would CrushGrid the cracker for ~9680 intensity.

3. STATIC TETHER. `AddComp<ForceAnchorComponent>` is enough and needs no helper (MapInit is re-raised). It gets you Disable(force) + PreventGridAnchorChanges. The chunk already has ShuttleComponent from ShuttleSystem.OnGridInit, so the D-M release trap does not apply to it — but assert it anyway, because the release path (`RemComp` both + `Enable(force: true)` + read back BodyType) is F7's and a chunk built by some future non-grid-init path would be undroppable.

4. THE DROP MUST BE EXPLICIT. There is no configuration in which the automatic sweep drops an orbit-parked chunk: `WfIsOrbitLayer` and `BodyType.Static` both skip it before `RigidSetHasSupport` is ever consulted (Gravity.cs:93-97). F7 calls, in order: remove ForceAnchor + PreventGridAnchorChanges, `_shuttle.Enable(chunk, force: true)`, verify BodyType != Static, `EnsureComp<CEZGridFallerComponent>` with Velocity 0 and GravityTime = now (otherwise the 3 s grace from RefreshGridZPhysics silently delays the fall), then `TryEnterTransit((chunk, mapGrid), startProgress: 0.98f)` and check the bool. With no gravgen the faller then integrates on its own — GridGravity 0.15, terminal 1.2, so a four-gap fall is on the order of half a minute — and lands with impact well above GridCrashVelocity 0.35.

5. CRASH SIZING IS FINE AS SHIPPED, BUT MOVE THE PER-TILE LOOP OFF THE HOT TICK. 1500 tiles will not hang the server (per-tick bounds at Processing.cs:94-125), but `CrashGrid`'s 1500 `QueueExplosion` calls each scan the queue for a combine partner, so budget one visible tick spike plus a few seconds of degraded TPS with NodeGroup and Pathfinding paused. If that is unacceptable, raise `CrashTileIntensity`/`MaxCombineDistance` or skip the per-tile loop for chunks above some tile count and keep only the centre blast — the centre blast alone (7500 intensity, slope 5, cap 100) is already a crater.

6. DELETE THE CHUNK ON A DELAY, NOT IN THE CRASH TICK. Every explosion CrashGrid queues is anchored to the chunk grid's own EntityCoordinates, and SpawnExplosion returns null for a terminating epicentre entity (ExplosionSystem.cs:427-428). QueueDel in the same tick deletes the chunk AND cancels the entire crash. Either wait until `_explosionQueue` has drained for that grid, or re-queue the crash in map coordinates on the ground layer before deleting. Players aboard become ghosts via MindSystem.cs:76 — acceptable per the design ("anyone still on the chunk goes down with it") but log it.

7. HOLE SEMANTICS. Answer the design question explicitly in the plan: the chunk lands ON the ground layer's plane, never inside the hole. HasGroundUnderFootprint tests the chunk's whole world AABB against the ground map-grid and returns true on the first non-empty tile, and the AABB of a circle always overhangs onto intact surface; and even if it did not, depth 0 has no map below so SetTransitAltitude's `progress < 0` branch lands unconditionally. Since the crack-hole is a real tile anyway, "in the hole" is purely visual — the crater decals and the hole tile texture under the landed chunk. Keep it that way: making the hole empty tiles would break the crash gate at Gravity.cs:384 in the unloaded-biome case and invite Smimsh's ReserveTiles to backfill it.

8. STAMP THE HOLE THROUGH ModifiedTiles. Both the landing Smimsh's `ReserveTiles` and BiomeSystem.OnShuttleFlatten will overwrite or backfill hole tiles that are not already in `BiomeComponent.ModifiedTiles`. `ReserveTiles` marks existing non-empty tiles as modified for you (PlanetSetup.cs:87-93), so calling it over the circle immediately after stamping is the cheapest guarantee.

9. WATCHDOG. `WFPlanetChunkComponent { NetEntity? Cracker }` plus a 1 Hz `_nextSweep` sweep in the same shape as WFGravityAnchorSystem.Update, dropping when `!TryGetEntity(Cracker, out var c)`, `TerminatingOrDeleted(c)`, `EntityManager.IsQueuedForDeletion(c)`, or `!HasComp<WFOrbitLayerComponent>(Transform(c).MapUid)`. Reuse the exact drop routine from item 4 so D24 and F7 cannot diverge. CleanupOrphanedTransitMaps is the precedent for the guard set.

10. LIGHTING AND ATMOS ARE PLAYER-FACING DECISIONS, NOT BUGS — BUT DECIDE THEM. The chunk in orbit is black-ambient AND self-roofed. If the intent is "EVA on a lit rock", the chunk needs either its own MapLight-equivalent (there is none per-grid; you would need PointLight entities spawned around the circle) or `RemComp<ImplicitRoofComponent>` plus `orbitComponents: [- type: MapLight]`. Adding MapLight to the orbit layer is one YAML line and lights every parked ship too, which is probably what the crew wants; removing ImplicitRoof from the chunk is one RemComp. Pick one and write it into the F5 plan, because "the chunk is invisible" will otherwise read as an overlay bug.

11. TEST HOOKS worth writing headless, in the existing PlanetNetworkTest fixture style: a static grid placed beside another on the orbit layer forms no CEZGridNetworkComponent; a 1500-tile grid gains GridAtmosphereComponent unless RemComped; a gravgen-less chunk grid with Inherent gravity leaves a mob non-weightless while one without it does not; TryEnterTransit(0.98f) on an orbit-layer chunk returns true only after PreventGridAnchorChanges is removed and BodyType is Dynamic; a chunk whose AABB straddles hole and intact surface reports HasGroundUnderFootprint true; CheckTransitCollisions produces no Smimsh when only one set is in transit; and CrashGrid followed by same-tick QueueDel produces zero explosions (the regression guard for item 6).

### Risks

- D3 'the chunk has no atmosphere' is broken by default, not by omission. AutomaticAtmosSystem.OnMassDataChanged (Content.Server/Atmos/EntitySystems/AutomaticAtmosSystem.cs:22-32) adds GridAtmosphereComponent to any grid whose FixturesMass / 0.5 reaches 7 tiles. A ~1500-tile chunk passes by 200x, so the chunk arrives with a simulated 1500-tile atmosphere and the comment at :34-36 says it is never removed again. There is no opt-out component to add to the prototype; F5 must RemComp after the SetTiles batch, and any later tile addition to the chunk re-triggers it.
- QueueDel on the chunk in the crash tick silently cancels the entire crash. CrashGrid queues every explosion at EntityCoordinates parented to the chunk grid (CEZLevelsSystem.Gravity.cs:413) and the centre blast resolves to a grid too (ExplosionSystem.cs:312 -> SharedTransformSystem.Component.cs:1490-1494); SpawnExplosion returns null on TerminatingOrDeleted(epicentre entity) (ExplosionSystem.cs:427-428). F7's 'delete the grid after the crash' is one tick away from producing no crater at all, with no log.
- A freshly created chunk grid is a live shuttle before anyone anchors it. ShuttleSystem.OnGridInit EnsureComps ShuttleComponent (ShuttleSystem.cs:135) and ShuttleComponent.Enabled defaults true (ShuttleComponent.cs:9), so OnShuttleStartup flips it to Dynamic / InAir / free rotation (:156-158). Between creation and AddComp<ForceAnchorComponent> the 750-mass chunk can be shoved, rotated, or bumped out of the berth, and anything that fires an event in between (Smimsh, tile writes, PVS) widens that window.
- Crew on the chunk in orbit are weightless and the code reads as if they would not be. The chunk grid gets a GravityComponent from SharedGravitySystem.OnGridInit (:202-205) but with Enabled false, the orbit map has no GravityComponent at all (planets.yml:40 orbitComponents: []), and EntityGridOrMapHaveGravity checks only those two (:170-171). Nothing in F0/F1/F3 writes gravity onto a grid without a gravgen, so this has to be done deliberately, with Inherent = true or GravitySystem.RefreshGravity (:24-25, :38-49) will wipe it the next time any gravgen anywhere changes.
- The chunk is unlit and self-shadowed in orbit. WFPlanetNetworkSystem does RemComp<MapLightComponent>(orbit) (:214) and the engine falls back to sRGB black (MapLightComponent.cs:15, Clyde.LightRendering.cs:682-683); on top of that the chunk keeps ImplicitRoofComponent with Color Black (ShuttleSystem.cs:141, ImplicitRoofComponent.cs:11-12) because CEZLevelsRoofSystem only strips it from grids in a z-grid network (CEZLevelsRoofSystem.Grids.cs:46-48) and the chunk is deliberately networkless. Expect 'the chunk did not spawn' bug reports.
- The parked chunk is a valid GridCleanup target. GridCleanupSystem.ShouldEntityCleanup's planetmap escapes both miss it — no MapComponent, and its parent orbit map has no MapGridComponent (Content.Server/_Mono/Cleanup/GridCleanupSystem.cs:61-62). It then depends on nearby players within 628 tiles, an IFF label it will not have, or AppraiseGrid exceeding 30000, over a 30-minute accumulator (CCVars.Mono.cs:41, :47, :59). A crew that leaves a mined-out chunk parked while they fly off can lose it to cleanup rather than to the disconnect protocol.
- An empty-tile hole would be filled in by the landing itself. Smimsh calls _biomes.ReserveTiles on every fixture AABB (ShuttleSystem.FasterThanLight.cs:1421), which generates biome tiles into empty indices (BiomeSystem.PlanetSetup.cs:95-106), and BiomeSystem.OnShuttleFlatten regenerates biome tiles for every flattened index not already in ModifiedTiles (BiomeSystem.cs:151-171). The design's crack-hole tile saves this, but only if F5 also marks those indices modified; a bare _mapSystem.SetTiles does not.
- CrashGrid's queueing cost is O(tiles x queued explosions) inside one synchronous tick. QueueExplosion scans every already-queued explosion for a combine partner (ExplosionSystem.cs:387-400); 1500 calls against a surviving lattice of several hundred entries is a six-figure TryDistance count in the CrashGrid loop itself, before any explosion has processed. The processing that follows is bounded (100 tiles/tick, 7 ms, Processing.cs:93-94) but pauses NodeGroupSystem and Pathfinding for its whole duration (:116-122). Not a hang; a multi-second TPS dip attributable to one event.
- The drop's crash can be skipped entirely if the biome under the site is unloaded at the moment of landing. IntegrateFallingGrid's crash gate requires HasGroundUnderFootprint on the landed map (Gravity.cs:382-385) and that reads live tiles; UnloadTiles writes Tile.Empty back for unmodified indices about 10 s after the last viewer leaves (BiomeSystem.ChunkLoader.cs:294, BiomeSystem.cs:60). CE z-eyes descending ten levels (F0 risk, CEZLevelsSystem.View.cs) usually keep the site loaded under an orbiting crew, which means the failure is intermittent and viewer-dependent — the worst shape for a bug.
- If F5 ever links cracker and chunk into a real CE grid network to model the tether, CEZGridSyncSystem takes over both poses. IsStaticAnchor returns true for any non-Dynamic body (CEZGridSyncSystem.cs:170-177), so HasStaticAnchor flips, UpdateBeforeSolve zeroes velocities and UpdateAfterSolve hard-pins every member to anchor+offset each tick (:411-424, :448-454, :469-495), and OnGridMoved teleports back anything that moves (:133-143). ## Effects on two grids and the surface

### Summary

EFFECTS API map for two grids + surface, verified against this worktree.

SHAKE. `SharedGravitySystem.StartGridShake(uid, gravity)` (Content.Shared/Gravity/SharedGravitySystem.Shake.cs:32) adds/refreshes `GravityShakeComponent` with a hard-coded `ShakeTimes = 10` (:46) at `ShakeCooldown = 0.2f` (:6) — 2 s per call, no intensity or duration parameter. It requires a `GravityComponent` on the target (Resolve at :37, and `UpdateShake` removes the component the moment the gravity comp is missing, :18-22). Every grid gets one automatically (`SharedGravitySystem.OnGridInit` EnsureComp, SharedGravitySystem.cs:202-205), and a biome planet's MAP entity gets both `MapGridComponent` and `GravityComponent` (BiomeSystem.PlanetSetup.cs:30,:43-46) — so `StartGridShake` works on the ground layer map, on the cracker hull grid and on a freshly-extracted chunk grid with no extra setup. The kick is client-side and local-player only: `GravitySystem.ShakeGrid` (Content.Client/Gravity/GravitySystem.Shake.cs:40-60) kicks only when `xform.GridUid == uid`, with `GravityKick = 100f` (Shake.cs:5) through a random unit-ish vector. TO SHAKE A SECOND GRID: call `StartGridShake` once per grid entity (hull AND chunk), every 2 s while the effect should persist. There is no radius — shaking the ground map shakes every player on the whole planet surface equally.

RECOIL (per-player, with falloff). `SharedCameraRecoilSystem.KickCamera(uid, kickback, comp?)` (Content.Shared/Camera/SharedCameraRecoilSystem.cs:53); the server override just `RaiseNetworkEvent(new CameraKickEvent(...), euid)` to that one player's session (Content.Server/Camera/CameraRecoilSystem.cs:9-15), and the client clamps to `KickMagnitudeMax = 1f` (SharedCameraRecoilSystem.cs:31) and multiplies by the `ScreenShakeIntensity` CVar, returning early when it is 0 (Content.Client/Camera/CameraRecoilSystem.cs:32-40). The canonical "near the anchors" pattern is `ExplosionSystem.CameraShake` (Content.Server/Explosion/EntitySystems/ExplosionSystem.cs:498-519): `Filter.Empty().AddInRange(epicenter, range, _playerManager, EntityManager)` then per-player `KickCamera(-delta.Normalized() * 5 * sqrt(intensity) * (1 - distance/range))`. `Filter.AddInRange` is same-map only (RobustToolbox/Robust.Shared/Player/Filter.cs:160-171), so this covers surface players and nobody in orbit.

AUDIO. `PlayPvs(sound, EntityCoordinates)` (RobustToolbox/Robust.Shared/Audio/Systems/SharedAudioSystem.cs:615, server impl Robust.Server/Audio/AudioSystem.cs:155-174) spawns an ordinary audio entity at those coordinates with no filter — pure PVS. `PlayStatic(sound, filter, coords, recordReplay, params)` (:670/:694) is the same but with an explicit session filter (server `AddAudioFilter` → `_pvs.AddSessionOverrides`, Robust.Server/Audio/AudioSystem.cs:67-81), so it reaches named players regardless of range. `AudioParams.WithLoop(true)` (AudioParams.cs:220); `MaxDistance` defaults to `DefaultSoundRange = 15` (SharedAudioSystem.cs:45, AudioParams.cs:100) and `WithMaxDistance` (:184) raises it. THE CROSS-LAYER ANSWER: a `PlayPvs` sound at the anchors is replicated to orbiting players (their CE z-eyes are view subscribers on the ground map, CEZLevelsSystem.View.cs:170-184,:204-212, `MaxZLevelsBelowRendering = 10`), but the client SILENCES it — `ProcessStream` sets `Gain = 0f` whenever `listener.MapId != xform.MapID` for any non-global audio (RobustToolbox/Robust.Client/Audio/AudioSystem.cs:397-403), and the listener is the local eye on the player's OWN map (:358-361). So positional audio never crosses a z-layer. The two working routes are (a) `PlayGlobal(sound, filter, ...)` — the entity stays in nullspace with `Global = true` (Robust.Server/Audio/AudioSystem.cs:84-93) and plays at full volume with no attenuation for that filter, or (b) a SECOND `PlayStatic` audio entity placed at the same world XY on the orbit map, filtered to orbit players, which keeps attenuation. For a hull-wide rumble the shipped pattern is `PlayPvs(sound, gridUid)` + `SetGridAudio(audio)` + keep the handle + `_audio.Stop(handle)`, exactly as FTL does (Content.Server/Shuttles/Systems/ShuttleSystem.FasterThanLight.cs:1669-1672,:859-861,:634-636; FTLComponent.TravelSound Content.Shared/Shuttles/Components/FTLComponent.cs:59-63). `SetGridAudio` (SharedAudioSystem.cs:146-173) sets `MaxDistance = max(gridExtents) + 15`, `ReferenceDistance = extents`, `NoOcclusion` and the `GridAudio` flag so the sound is heard from the grid's centre everywhere aboard. `CEFilter.ZPvs/ZPvsExcept` (Content.Shared/_CE/ZLevels/Core/CEFilter.cs:26,:69) exists for cross-layer filters but only adds ONE map above the origin plus maps below, so from a ground-layer origin it does NOT reach depth-4 orbit; build the orbit filter yourself from `WFPlanetNetworkComponent`.

AMBIENT HUM. `AmbientSoundComponent` (Content.Shared/Audio/AmbientSoundComponent.cs:13) with `Enabled`(:15) `Sound`(:20) `Range` default 2(:27) `Volume` default -10(:36), toggled from the server via `SharedAmbientSoundSystem.SetAmbience/SetRange/SetVolume/SetSound` (Content.Shared/Audio/SharedAmbientSoundSystem.cs:20,30,45,54). This is the F3 convention already in the feature: anchors.yml:97-102 (`circular_saw.ogg`, range 12, enabled false) driven by `WFGravityAnchorSystem.cs:71` on the Drilling edge, and machines.yml:66-71 (`gravity_gen_hum.ogg`, range 10) for the centrifuge. EFFECT ENTITIES. The `SpawnDustPuff` pattern is `Spawn(protoId, new EntityCoordinates(map, pos + jitter))` (Content.Server/_CE/ZLevels/Core/CEZLevelsSystem.PilotControl.cs:276-279) against a prototype that is nothing but `TimedDespawn` + `Sprite` (Resources/Prototypes/_CE/Entities/zeffects.yml:1-12, lifetime 0.4). For an ANIMATED one-shot the upstream template is `EffectEmpPulse` (Resources/Prototypes/Entities/Effects/emp_effects.yml:1-19): `TimedDespawn` + `Sprite` with an `unshaded` layer + `EffectVisuals` + `AnimationPlayer`, where `EffectVisualizerSystem` deletes the entity on animation completion (Content.Client/Effects/EffectVisualizerSystem.cs:10-16). Spawned effect entities go through PVS, which means they DO reach orbiting viewers through the z-eyes (unlike the audio) — spawn, don't RaiseNetworkEvent, when the effect must be seen across layers. The `RaiseNetworkEvent` alternative is `SharedColorFlashEffectSystem.RaiseEffect(color, entities, filter)` (Content.Shared/Effects/SharedColorFlashEffectSystem.cs:7 / Content.Server/Effects/ColorFlashEffectSystem.cs:8-11, client `SubscribeAllEvent` Content.Client/Effects/ColorFlashEffectSystem.cs:28): cheaper (no entity, no PVS churn), but you must supply the filter yourself — `RaiseNetworkEvent(msg)` broadcasts to the WHOLE server (RobustToolbox/Robust.Shared/GameObjects/EntitySystem.cs:159), `(msg, Filter)` is the targeted form (:190), and `(msg, EntityUid)` sends only to that entity's own session (:206) — there is no "PVS of this point" overload.

RING: DECALS vs OVERLAY — RECOMMEND THE OVERLAY for the growing ring, decals only for the permanent rim stamped once at extraction. Geometry: cut radius is d/2 + 2 with d in 16..40 (design §5, D21), so radius 10..22 and a perimeter of 2πr = 62.8..138.2 tiles — 63 to 139 decals for ONE full ring at one decal per perimeter tile, doubling to ~278 if `crack_rim` gets its own ring beside `crack_ring`. Decal chunks are 32 tiles (Content.Shared/Decals/SharedDecalSystem.cs:21), so a 44-tile circle spans a 2x2 to 3x3 chunk block (4-9 chunks) and the perimeter clips every one of them (a 32-chunk's corner sits 22.6 tiles from its centre, just outside r=22). There is NO per-chunk decal cap anywhere in engine or content. The cost is in the send path, not the add: `TryAddDecal` is cheap (Content.Server/Decals/DecalSystem.cs:304-329) but `DirtyChunk` (:287-294) makes `SendChunkUpdates` re-serialise the ENTIRE `DecalChunk` dictionary of each dirtied chunk to every viewer that has it in range (:569-598) — not a delta. So an 8-stage growing ring re-sends the whole accumulated ring (~139 decals x ~40-60 B = 6-8 KB) per stage per viewer at the top end, and F8's round-persistent fissure decals (D19) land in the same chunks and inflate every one of those resends. Removal has no bulk API: per-id `RemoveDecal` (:331), each dirtying its chunk again, and you must retain the `uint` ids yourself (`GetDecalsIntersecting` at :356 is the only recovery). Two hard traps make decals wrong for the ANIMATION: (1) `DecalSystem.OnTileChanged` deletes every decal on any tile that becomes space (:165-206, space = tile def `MapAtmosphere`, Content.Shared/Maps/TurfSystem.cs:132-135), and biome unload writes `Tile.Empty` to any tile that still matches its generated biome tile (Content.Server/Parallax/BiomeSystem.ChunkLoader.cs:277-302) on a 10 s timer (BiomeSystem.cs:60) — ring decals on untouched ground are silently wiped; (2) the biome load area is only 16 tiles around each viewer or z-eye (BiomeSystem.cs:49, BiomeSystem.PlayerTracker.cs:70-78), so one orbiting player centred on the site keeps the middle loaded but NOT a perimeter at radius 22, which means the ring erases itself while the crew watches from orbit. Surviving that needs `ReserveTiles` (BiomeSystem.PlanetSetup.cs:76-107) or a stamped non-biome tile under every ring decal, i.e. 139 extra tile writes that each re-flood `CEZGridConnectorSystem` (its `TileChangedEvent` handler marks dirty for the whole world, CEZGridConnectorSystem.cs:105). By contrast `WFCrackCircleOverlay` already draws the exact circle from the two anchors' networked state (Content.Client/_WF/PlanetCracker/Anchors/WFCrackCircleOverlay.cs:71-137), caches vertices per pair (:143-165), emits ONE `DrawPrimitives` LineStrip (:118) at `clamp(radius*8, 64, 256)` = 176 segments for r=22 (:154), costs zero bandwidth beyond one float of crack progress on an existing `AutoNetworkedField`, needs only `ring.Vertices.Span[..n]` to draw an arc for staged growth, and — because it filters on `xform.MapID == args.MapId` (:84-85) and runs once per z-pass — is already visible from orbit through the z-view once the cloud layer is dropped per F4. Its known cost is the F1F3 open risk of ~500 lines/frame across three passes; a cached render target is the escape hatch if F5 draws several sites.

### Recommendations

RING: use the OVERLAY for the growing ring; use decals only once, at the extraction moment, for the permanent hole rim.

Reasons, in order of weight:
1. Durability. Ring decals on ordinary biome tiles are deleted by DecalSystem.OnTileChanged whenever the tile becomes space, and BiomeSystem.UnloadTiles writes Tile.Empty to every unmodified tile of any chunk that no viewer or z-eye has been within 16 tiles of for 10 s (BiomeSystem.cs:49,:60; PlayerTracker.cs:70-78; ChunkLoader.cs:277-303). A 22-tile-radius perimeter is outside the load box of a player standing at the circle centre, so the ring erases itself piecemeal during the very 12-20 minutes it is supposed to grow. The overlay is derived from the two anchors' networked state and cannot rot.
2. Bandwidth shape. DecalSystem re-sends whole 32-tile chunks, not deltas (DecalSystem.cs:569-598). Eight stages over 4-9 dirtied chunks means the last stage resends the entire accumulated ring (63-139 decals, ~6-8 KB) to every surface AND orbit viewer, and F8's round-persistent fissure decals (D19) ride along in the same chunks. The overlay costs one extra float on a component that is already AutoNetworkedField.
3. It already exists and already works across layers. WFCrackCircleOverlay draws the exact circle, caches its vertices, and re-runs per z-pass with the `xform.MapID == args.MapId` filter (WFCrackCircleOverlay.cs:84-85), so once F4's cloud-layer drop lands the growing arc is visible from orbit for free. Staged growth is `ring.Vertices.Span[..n]` where n = (int)(segments * progress) - no new draw path, no new prototypes, no new assets.
4. Decals still earn their place ONCE. At extraction, stamp crack-hole tiles inside the circle and lay one crack_rim ring on the tiles just outside it. Those are ~139 one-time adds in a single tick, they persist because the adjacent crack-hole tiles make the area 'modified' (or ReserveTiles it explicitly), and the permanent scar is exactly what the design asks for ('the rim gets a decal ring', design §F5 line 208).

### Risks

- CROSS-LAYER AUDIO IS SILENT, NOT QUIET. Robust.Client/Audio/AudioSystem.cs:399-403 zeroes the gain of any non-global audio whose map differs from the listener's. Orbiting players DO replicate the audio entity (their CE z-eye is a view subscriber on the ground map) so nothing errors and nothing logs - the sound simply is not there. Any plan that says 'the rumble at the anchors is heard faintly from orbit' is wrong; it needs either PlayGlobal with an explicit filter or a duplicate audio entity placed on the listener's own map.
- GravityShake HAS NO RADIUS AND NO INTENSITY. ShakeTimes is hard-coded to 10 at 0.2 s (SharedGravitySystem.Shake.cs:6,:46). Calling StartGridShake on the planet ground map shakes every player anywhere on that planet identically, including someone 500 tiles from the site. 'Shaking near the anchors' must be KickCamera with a distance filter, not StartGridShake.
- THE CLIENT'S ShakeGrid GUARD HAS A DEAD CLAUSE. `xform.GridUid != uid || xform.GridUid == null && xform.MapUid != uid` (Content.Client/Gravity/GravitySystem.Shake.cs:52-56): if GridUid is null the first clause is already true, so the map-level branch never runs. Players parented directly to a gridless map - which the F0 orbit map is, by design (no map grid) - never receive the camera kick even when the map entity is shaken. Shake the ship grid. The audio branch at :28-32 does not share the bug, so a map-level shake produces sound with no shake, which will read as 'the shake is broken'.
- ANY SHAKE OR KICK CAN BE TURNED OFF BY THE PLAYER. Content.Client/Camera/CameraRecoilSystem.cs:33-34 returns immediately when CCVars.ScreenShakeIntensity is 0. Never carry information (a warning, a countdown cue) only in shake.
- RING DECALS WILL VANISH MID-CRACK. Biome unload writes Tile.Empty to unmodified tiles of any chunk with no viewer or z-eye within 16 tiles for 10 s (BiomeSystem.cs:49,:60; ChunkLoader.cs:277-303), and DecalSystem.OnTileChanged then deletes their decals (DecalSystem.cs:165-206). At radius 22 the perimeter is outside the load box of a player standing at the centre, so parts of the ring erase themselves while the crack runs. This is the F1F3 'biome unload semantics' open risk landing squarely on F5's ring.
- DECAL UPDATES ARE WHOLE-CHUNK, NOT DELTA. DecalSystem.SendChunkUpdates (:569-598) serialises the complete Dictionary<uint, Decal> of every dirtied 32x32 chunk to every viewer. A staged ring therefore pays for the whole accumulated ring at every stage, to surface AND orbit viewers, and F8's round-persistent fissure decals (D19) inflate the same chunks for the rest of the round.
- THERE IS NO BULK DECAL REMOVAL. Only per-id RemoveDecal (DecalSystem.cs:331), each re-dirtying its chunk. You must retain every out decalId; the only recovery is GetDecalsIntersecting (:356), which walks every decal in every chunk the box touches. Clearing a 139-decal ring is 139 removals and up to 9 more chunk resends.
- STAMPING CRACK-HOLE TILES WILL WIPE ANY DECAL ALREADY ON THEM if the tile definition sets mapAtmosphere true (DecalSystem.cs:172-173 via TurfSystem.IsSpace at :132-135). Order matters: stamp tiles first, then lay the rim ring on the tiles OUTSIDE the hole, or give crack_hole mapAtmosphere false.
- EVERY TILE WRITE IN THE CIRCLE RE-FLOODS THE CE GRID CONNECTOR. CEZGridConnectorSystem marks itself dirty on any TileChangedEvent anywhere in the world (CEZGridConnectorSystem.cs:105, flagged in the F1F3 open risks). Extraction stamps ~1500 tiles for a radius-22 circle; a per-tile-event flood is the hammer that risk predicted.
- AMBIENT SOUND IS CLIPPED TO ~8 TILES AND CAPPED AT 16 SOURCES. The client samples a box of CCVars.AmbientRange (default 8, CCVars.Audio.cs:16-17) regardless of a component's Range, keeps at most MaxAmbientSources = 16 with 6 per path (AmbientSoundSystem.cs:58,:274), and never crosses a map (:279-280). The anchor's Range: 12 is already being clipped today. Do not use AmbientSound for anything that should be audible across a 44-tile circle.
- CVars.AudioZOffset defaults to -5f (CVars.cs:1322), so GetAudioDistance adds a constant 5 tiles to every positional sound (SharedAudioSystem.cs:274-277). A MaxDistance of 15 is really ~14.1 tiles of audible radius, and a sound authored to just reach the circle edge will fall short.
- A SPAWNED EFFECT ENTITY ON THE GROUND MAP IS REPLICATED TO EVERY ORBITING PLAYER, because z-eyes exist for all 10 levels below with a PVS scale multiplied by (1/0.85)^levelsBelow (CEZLevelsSystem.View.cs:170-177,:214-233). A per-tile burst around a 139-tile perimeter is 139 entities entering the PVS of both surface and orbit viewers in one tick.
