D-C. THE CONSOLE LISTS THE WHOLE STAR SYSTEM, NOT ONLY THE REGISTRY. D-D. THE RATING IS DERIVED SERVER-SIDE AND ONLY THE ENUM TRAVELS. OrePrototype (Content.Shared/Mining/OrePrototype.cs:10-26) has ID/OreEntity/MinOreYield/MaxOreYield/OreSprite and NO value or price field, so a rating cannot be derived from ore identity. D-E. DEEP VEINS ARE A FLAT-MODE BIOME MARKER LAYER WITH A SELF-DELETE TILE WHITELIST. BiomeMarkerLayerPrototype has EXACTLY eight fields — ID :12, EntityMask :18, Prototype :24, Radius :30, MaxCount :36, MinGroupSize :42, MaxGroupSize :48, Size :52. There is NO CheckTile and NO tile whitelist (tile whitelists live on biome LAYERS, IBiomeWorldLayer.AllowedTiles, consumed at SharedBiomeSystem.cs:227-229; marker layers never consult them). Flat mode (`prototype:`) is mandatory: entityMask mode substitutes an existing rock (BiomeSystem.MarkerProcessor.cs:184-190 / :285-296), the opposite of "hidden". WFBiomeAsclepiu is Grasslands + MonoOcean + Snow (Resources/Prototypes/_WF/PlanetCracker/biomes.yml:6-32) so a flat layer WILL place veins in the sea and on the icecap; the vein's own MapInit handler resolves its tile and QueueDels itself when the tile is not in WFDeepVeinComponent.AllowedTiles (default FloorPlanetGrass, FloorPlanetDirt — Grasslands' fill tiles, Resources/Prototypes/Procedural/biome_templates.yml:124-130).

D-F. THE VEIN PROTOTYPE MUST ANCHOR ITSELF. BiomeSystem.LoadChunkMarkers does CreateEntityUninitialized + RemComp(GhostTakeover/GhostRole) + InitializeAndStartEntity (MarkerProcessor.cs:305-308) and NEVER calls AnchorEntity, unlike LoadEntities (BiomeSystem.ChunkLoader.cs:118-123). `- type: Transform / anchored: true` on the prototype is the whole fix; SharedTransformSystem honours it on init, and LoadChunkMarkers forces the underlying biome tile to exist first (MarkerProcessor.cs:285-289) so the empty-tile refusal cannot fire. Without it F5 step 5 takes the UNANCHORED SetParent branch and the vein loses its tile index, silently breaking F6. A second, load-bearing consequence of being anchored: UnloadTiles' first check is `if (HasAnchoredEntity(...)) { modified.Add(indices); return; }` (BiomeSystem.ChunkLoader.cs:278-283) and UnloadChunk writes that set back (:196-198), so a SURVIVING vein pins its own tile against regeneration at unload time. A deleted one does not (see section 8).

D-G. DETERMINISM IS OPT-IN DATA, NOT A HASH. === 3. THE SURVEY CONSOLE BUILD STATE ===

BuildState(console):
 1. Resolve the console's SECTOR position. `var xform = Transform(console); var mapUid = xform.MapUid;`
    a. If mapUid carries WFOrbitLayerComponent or WFPlanetLayerComponent the hull is inside a planet network; resolve the anchor body with F5's `SharedWFCrackerSystem.TryGetPlanetFromOrbit(mapUid, out var body)`, else `WFPlanetLayerComponent.Network -> WFPlanetNetworkComponent.Planet`, and use `_transform.GetWorldPosition(body)`.
    b. Else if mapUid carries StarSystemMapComponent, use `_transform.GetWorldPosition(xform.GridUid ?? console)` (the WFCrackConsoleSystem.cs:231-237 recipe).
    c. Else ConsolePositionKnown = false and every row gets DistanceKnown = false. NEVER emit a meaningless number.
 2. Find the sector map: `AllEntityQuery<StarSystemMapComponent>()`, first with a non-null `System`. Index the StarSystemPrototype and iterate `.Planets`; for each entry compute `pos = new Vector2(MathF.Cos(e.Angle), MathF.Sin(e.Angle)) * e.Distance` (bit-identical to WFPlanetRegistrySystem.cs:62) and the display name from `_proto.Index(e.Planet).Name`.
 3. Join the registry: one pass of `AllEntityQuery<WFSectorPlanetComponent>()` into a scratch dictionary keyed by the surface prototype's PlanetType. Registered rows carry Planet = GetNetEntity(body), HasSurface = true, Sanctioned = comp.Sanctioned, Cracked = comp.Cracked (F5's field), Name = `MetaData(body).EntityName`, Beacon = that same string, HasBeacon = `HasComp<FTLBeaconComponent>(body)`.
 4. Vein rating: `comp.Surface -> WFPlanetSurfacePrototype.Veins -> WFVeinTablePrototype`; `SharedWFSurveySystem.Rate(Score(table, comp.Sanctioned), bands)`. VeinsKnown = false when the surface has no Veins.
 5. Distance: raw `Vector2` subtraction, `(row.SectorPos - consoleSectorPos).Length()`. NEVER MapCoordinates.InRange — it returns false for differing MapIds before any maths (F4 D-H).
 6. Rows sorted by distance when ConsolePositionKnown, else by name.
There is no mark block, no message handling and no write path of any kind: the console is a read-only instrument.

D-O (NEW, CORRECTING REVISION 1). AN ANCHORED BODYLESS VEIN RIDES THE DYNAMIC SUNDRIES TREE. EntityLookupSystem's broadphase insert does `AddOrUpdateSundriesTree(..., staticBody: body?.BodyType == BodyType.Static, ...)` for anything with no PhysicsComponent or no CanCollide (EntityLookupSystem.cs:648-657), and AddOrUpdateSundriesTree picks `staticBody ? broadphase.StaticSundriesTree : broadphase.SundriesTree` (:491-496). A null body is not Static, so the vein lands in the DYNAMIC SundriesTree; anchoring never moves it. Query dispatch only reads StaticSundriesTree when BOTH Static and Sundries bits are set and reads SundriesTree whenever the Sundries bit is set (ComponentQueries.cs:165-174). `LookupFlags.Uncontained = Dynamic | Static | Sundries | Sensors` (EntityLookupSystem.cs:57) therefore finds veins, and so does StaticSundries — but only via its Sundries bit, and the Static bit contributes nothing. Revision 1's "StaticSundries is the tightest correct filter" was wrong; F2 uses Uncontained, the same flag F5 step 5's ride-up query uses, so the surveyor and the extraction agree by construction. Any future narrowing to LookupFlags.Static alone would return zero veins with no error.

=== 6. WHERE VEINS COME FROM, AND WHEN (CORRECTED) ===

Generation is driven by VIEW SUBSCRIBERS, not by a surface visit: BiomeSystem.ProcessPlayerChunkRequests runs the attached-entity branch AND every pSession.ViewSubscriptions entry (Content.Server/Parallax/BiomeSystem.PlayerTracker.cs:25-61), each calling AddChunksInRange (:70) and AddMarkerChunksInRange (:80); CanLoad (:65-68) excludes only ghosts. A CE z-eye under an orbiting hull is a view subscriber with no GhostComponent, so veins already exist under a parked cracker before anyone lands. Entities spawn only for chunks inside the 16-tile load area (BiomeSystem.cs:49, :65 `_loadArea`), through LoadChunks -> LoadChunkMarkers (BiomeSystem.cs:248-256). Marker-spawned entities are recorded only as chunk indices in BiomeComponent.LoadedMarkers (BiomeComponent.cs:74-75, written at MarkerProcessor.cs:91-99, read at :38-39) and are NEVER unloaded. So the surveyor is a REVEAL mechanic, never a generation trigger, and "hidden" must mean "not drawn and not examinable", never "not spawned".
CORRECTION TO REVISION 1: the claim that "LoadChunkMarkers adds each spawned node to ModifiedTiles, so the tile under a vein is pinned" is FALSE on a virgin chunk. LoadChunkMarkers does `component.ModifiedTiles.TryGetValue(chunk, out var modified); modified ??= _tilePool.Get();` (MarkerProcessor.cs:272-273), adds nodes to that local set (:309), and NEVER writes it back — its only touch of the dictionary is the `Remove` when the set ended up empty (:313-317). Worse for the claim, LoadChunks calls LoadChunkMarkers BEFORE LoadChunk for a first-time chunk (BiomeSystem.cs:249-255), so on first load the entry cannot already exist and the whole set is discarded. What actually pins a vein's tile is the vein being ANCHORED at unload time: UnloadTiles' first check is `if (HasAnchoredEntity(...)) { modified.Add(indices); return; }` (ChunkLoader.cs:278-283) and UnloadChunk writes that set back (:196-198). D-F's `anchored: true` is therefore load-bearing twice over.

=== 8. REJECTED CRITIQUES ===

REJECTED — "Every vein that deletes itself on the AllowedTiles check leaves its tile permanently pinned in BiomeComponent.ModifiedTiles" (minor). The premise is the same claim revision 1 made in §6, and the code refutes both directions: LoadChunkMarkers' `modified` set is NEVER inserted into component.ModifiedTiles. The method takes the set with `TryGetValue` then `??= _tilePool.Get()` (Content.Server/Parallax/BiomeSystem.MarkerProcessor.cs:272-273) and its only write to the dictionary is `component.ModifiedTiles.Remove(chunk)` when the set is empty (:313-317) — there is no `component.ModifiedTiles[chunk] = modified` anywhere in it, unlike FinalizeChunk (ChunkLoader.cs:166-175) and UnloadChunk (:190-199) which both do exactly that. And the ordering forecloses the "chunk already had an entry" case for the common path: LoadChunks calls `LoadChunkMarkers` first and only then `LoadChunk` for a chunk it is adding to LoadedChunks (Content.Server/Parallax/BiomeSystem.cs:249-255), so at marker time a first-visit chunk has no entry at all and every marker node — spawned, deleted, or surviving — is dropped on the floor. A self-deleted vein additionally leaves no anchored entity behind, so UnloadTiles' HasAnchoredEntity branch (ChunkLoader.cs:278-283) does not pin it either; its tile reverts normally, because LoadChunkMarkers had set it to exactly the tile TryGetBiomeTile computes (:285-289), which is the value UnloadTiles compares against (:284-290). There is therefore no pinning to bound and no ModifiedTiles growth assertion to add. The TRUE consequence, which revision 2 does fold in (D-F, §6), is the opposite one: a SURVIVING vein pins its own tile at unload, which is what F6 wants. The reviewer's sibling issue on the same code — that revision 1's §6 pinning sentence is wrong — is ACCEPTED and corrected in §6.

Tuned to 4 at r=10 it gives ~19 at r=22; tuned to 7 at r=22 it gives ~1.4 at r=10 and small circles will frequently contain ZERO veins. - FLAT-MODE DENSITY IS LOWER AND UNEVEN. GetMarkerNodes skips any tile the biome wants an entity on (MarkerProcessor.cs:176-179) and any tile that already holds an anchored entity (:158-162). Grasslands plants rock formations, trees and ponds (biome_templates.yml:77-121), so the effective vein density is materially lower than count/size^2 and varies by terrain. Do not tune maxCount from arithmetic alone.
- MARKER SEEDS DEPEND ON DICTIONARY ENUMERATION ORDER. markerSeed includes a per-layer index taken from iterating _markerChunks[biome] (MarkerProcessor.cs:30-34,:49), rebuilt every tick from the HashSet BiomeComponent.MarkerLayers (BiomeComponent.cs:77-78); the code's own comment at :32 admits ordering is not guaranteed. Adding WFDeepVeins re-rolls every ore layer's placement (cosmetic, accepted) and in principle a rehash could shift placement mid-round. The YAML comment now states this truthfully; DeepVeinTest.MarkerNodesAreDeterministic pins the per-layer maths but cannot pin the index.
- AN ANCHORED VEIN BLOCKS LATER MARKER LAYERS ON ITS TILE. GetMarkerNodes' `if (!forced && existing != null) continue` (:158-162) means any layer processed after WFDeepVeins skips a vein's tile entirely. Harmless against the eight entityMask ore layers (they need a rock there and a vein tile has none) but it will bite any future flat layer — F8's fissure seeds in particular.
- VEINS EXIST BEFORE ANYONE LANDS, AND FOREVER. A CE z-eye under an orbiting hull is a view subscriber with no GhostComponent, so CanLoad passes (BiomeSystem.PlayerTracker.cs:42-68) and marker chunks are built beneath any parked hull; marker-spawned entities are recorded only as chunk indices in BiomeComponent.LoadedMarkers and are never unloaded. A round-long orbit builds a permanent vein field across ground the crew never walked. Bounded (one pass per marker chunk, no mobs) but it means 'hidden' can only ever mean 'not drawn and not examinable'.
- MARKER NODES ARE NOT PINNED AT SPAWN; SURVIVING VEINS PIN THEMSELVES AT UNLOAD. LoadChunkMarkers takes its `modified` set with TryGetValue then a pooled fallback and NEVER writes it back (MarkerProcessor.cs:272-273 vs :313-317), and LoadChunks runs it BEFORE LoadChunk for a first-visit chunk (BiomeSystem.cs:249-255), so nothing a marker pass does reaches BiomeComponent.ModifiedTiles. What pins a vein's ground is the vein being anchored when the chunk unloads (ChunkLoader.cs:278-283, written back at :196-198). Consequence to watch: if the vein prototype ever loses `anchored: true`, or a future change deletes veins on unload, the tile is regenerated and F6's miner can end up over ground that no longer matches what was surveyed.
- THE REVEAL IS CLIENT-SIDE VISIBILITY, SO IT IS CHEATABLE. A networked vein with an invisible sprite layer is visible to a modified client, and Ore/TotalYield are networked so the numbers are too. Given 1,500-4,000 ore per vein this is a real economy exposure. The hardening path, if it is ever wanted, is to stop networking Ore/TotalYield and push them only to revealed viewers — which needs Component.SessionSpecific plus a ComponentGetStateAttemptEvent filter (the Revolutionary precedent, PvsSystem.GetStates.cs:46/:51/:98). A PVS-level hide via a new VisibilityFlags bit is NOT an option while a client overlay draws the veins.
- TWO CLIENT SYSTEMS WANT THE SAME SUBSCRIPTIONS ON WFSurveyedComponent. WFDeepVeinOverlaySystem owns ComponentInit/ComponentShutdown/LocalPlayerAttached/LocalPlayerDetached; WFDeepVeinVisualsSystem owns AfterAutoHandleStateEvent (on WFSurveyedComponent) and ComponentStartup (on WFDeepVeinComponent). Robust allows one directed subscription per (component, event) pair and crashes at start otherwise. Stage C must not drift from that split. The AfterAutoHandleState subscription is also coupled across worktrees: it compiles only because Stage A writes [AutoGenerateComponentState(true)] (AfterAutoHandleStateAnalyzer.cs:29-38 is an Error, not a warning).
- A DESTINATION DOES NOT APPEAR UNTIL THE PILOT PINGS. MapScreen rebuilds its destination tree only in PingMap (MapScreen.xaml.cs:266-283, cooldown at :282/:589); UpdateState (:125-142) just stores the beacon list. The console's hint line is the only thing that tells the crew this. Less severe than in revision 1 — the beacon has existed since round start, so a pilot who has pinged at any point already has it — but a fresh console still shows a name the map may not be displaying yet.
- THE CONSOLE'S ROWS ARE MOSTLY EMPTY BY DEFAULT. wf.planet_networks defaults false and is CVar.SERVERONLY (PlanetCrackerCVars.cs:15), and registration returns early when it is off (WFPlanetRegistrySystem.cs:50-51). The star-system enumeration means the list is still populated, but every row reads 'no crackable ground' and carries no rating. The client cannot read the CVar to explain why.
- ONE CRACKABLE WORLD EXISTS. WFSurfaceAsclepiu is the only wfPlanetSurface in the tree against five bodies in SystemKyphrus, so the vein rating column has exactly one meaningful value and the rating bands cannot be calibrated against a spread until more surfaces ship.
- A FIXED BIOME SEED CHANGES TERRAIN, NOT JUST VEINS. Setting WFPlanetSurfacePrototype.Seed makes Asclepiu's whole surface identical every round. That is the price of 'the same planet yields the same veins' and is why the field is opt-in per surface rather than a hard-coded hash. Confirm it is wanted before shipping the seed line in planets.yml.
- NO SURVEYOR SOUND ASSET IS SPECIFIED. ASSET_REQUIREMENTS' sound table (lines 59-72) has no survey ping or pulse row while the design (:149) says the surveyor pulses. F2 reuses /Audio/Machines/sonar-ping.ogg (MiningScannerViewerComponent.cs:26). Either add a row to ASSET_REQUIREMENTS or the two documents drift, which section 6 of the design explicitly forbids.
- deep_vein.rsi IS FILED AS A DECAL BUT CONSUMED AS AN ENTITY SPRITE. The asset lives under Resources/Textures/_WF/PlanetCracker/Decals/ and ASSET_REQUIREMENTS row 10 calls it a 1x1 decal, but marker layers spawn entities and never decals (MarkerProcessor.cs:305). Either move the rsi or amend the asset doc.
- surveyor.rsi's `scanning` STATE SHIPS UNUSED. F2 drops the scanning face outright (D-N) rather than spending a second subscription or a per-frame sweep on it, so the asset carries a state nothing reads. Note it in ASSET_REQUIREMENTS or accept the drift; the console's own idle/scanning pair IS wired.
- THE OUTPOST CONSOLE (D18) IS A MAPPING TASK THIS PLAN DOES NOT DO. Placing WFSectorSurveyConsole at the outpost means appending a `- proto: WFSectorSurveyConsole` document with a fresh uid and parent: 2 to Resources/Maps/_Mono/Outpost/caelestinus_central.yml beside the bridge console cluster at :24669-24692, plus ApcPowerReceiver and Battery blocks. That file is 69,378 lines and is the live map, so it is a merge-conflict magnet and should be done in the map editor. There is NO marker or spawn-rule route that ADDS an entity to a station grid at a chosen tile.
- THE TEST-ONLY SURFACE IN DeepVeinTest DIVERGES FROM THE SHIPPED ONE. Generation is proven against a grass-only [TestPrototypes] surface precisely because Asclepiu's ocean and snow layers make the shipped case seed-dependent. That means nothing in CI proves a vein ever survives on ASCLEPIU specifically. The mitigation is the density measurement listed in the second risk: run it on the real surface in a headless fixture and record the observed in-circle count before calling F2 playable.
- FORCING MARKERS IN A TEST BULLDOZES. BiomeSystem's forced path deletes any anchored entity found on a candidate tile (MarkerProcessor.cs:58-70) and ForcedMarkerLayers is cleared at the end of each pass (:118). The fixture helper is safe because it runs on a fresh test stack, but it must never be reached for from production code.
